# 문제 생성 흐름도 — PDF를 올리면 문제집이 만들어지기까지

> 만들어진 문제가 합격 판정을 받는 과정은 **[문제 검증 흐름도](QUIZ_FLOW_VALIDATION.md)** 에서 이어집니다.
> 이 문서의 예시는 전부 하나의 사례로 이어집니다: **정보처리기사 교재 → "7. SQL문 활용" 단원 → "HAVING" 개념 → 단답형 문제 1개**.

## 전체 흐름 한눈에 보기

```
사용자가 PDF를 올린다
   │
   ▼
1단계  자료 분석(파싱, 팀원 파트) — 끝나면 목차·조각·문장 위치·개념을 넘겨받는다
   ▼
2단계  문제 만들기 시작 — 분석이 끝나면 자동으로 시작된다
   ▼
3단계  재료를 생성기 입력 형태로 변환
   ▼
4단계  재료 이상 없는지 확인 (이상하면 여기서 중단)
   ▼
5단계  출제할 개념 고르기 — 개념마다 "근거 문장" 찾기
   ▼
6단계  출제 계획 세우기 — 단원별 몇 문제, 어떤 유형
   ▼
7단계  AI가 문제 만들기 ★
   ▼
8단계  기본 점검 (빈칸 문제는 코드가 조립)
   ▼
9단계  품질 검증 — 다른 AI들이 검토하고 직접 풀어본다 (별도 문서)
   ▼
10단계  합격한 문제만 데이터베이스에 저장
   ▼
11단계  사용자가 문제를 푼다 — 안 푼 문제부터, 부족하면 복습
```

**핵심 원칙 하나**: 모든 문제의 정답은 반드시 **교재 원문 문장으로 입증**되어야 합니다. AI가 아는 지식으로 지어내는 것은 금지 — 그래서 모든 문제에는 "근거 문장"이 붙어 있고, 풀이 화면에서 📎 교재 원문으로 보여줍니다.

---

## 0단계. PDF 올리기

| | |
|---|---|
| 들어오는 것 | PDF 파일 |
| 하는 일 | 업로드 요청을 받으면 바로 응답하고, 분석은 백그라운드에서 진행 (몇 분 걸리기 때문) |
| 나가는 것 | 문서 번호 + 진행 상태 |

화면은 몇 초마다 서버에 진행 상태를 확인해서 보여줍니다. 같은 파일을 또 올리면 이미 있는 결과를 재사용합니다.

## 1단계. 자료 분석(파싱) 결과 넘겨받기

자료 분석 자체는 파싱 파트(팀원 담당)의 일입니다. 문제 생성 입장에서 중요한 건 **분석이 끝나면 아래 4가지를 넘겨받는다**는 것입니다:

| 넘겨받는 것 | 무엇인가 | 문제 생성에서 어디에 쓰나 |
|---|---|---|
| 목차 | 단원 구분과 각 단원에 속한 조각 목록 | 문제를 단원별로 귀속시키고, 단원별 출제량을 정할 때 |
| 조각 | 본문 텍스트를 적당한 크기로 나눈 덩어리 | 문제 생성의 작업 단위 (조각 하나당 AI 호출 1번) |
| 문장 위치 정보 | 조각 안 문장마다 기록된 정확한 위치 | 문제의 근거를 문장 단위로 지정하고, 풀이 화면에서 "교재 13쪽의 이 문장이 근거"라고 보여줄 때 |
| 개념 목록 | 조각마다 뽑아둔 핵심 개념 (이름 + 설명 + 어느 문장에 나오는지) | 출제 후보 — 개념마다 문제가 1개 이상 만들어진다 |

이 밖에 "그림 없이는 이해가 안 되는 위치" 정보도 함께 받아서, 그런 문장은 출제에서 제외합니다.

**예시** — 팀원 쪽에서 실제로 넘어오는 모양 (파싱의 "문서 트리" 조회 결과, 일부만 발췌):

```json
{
  "document": { "filename": "정보처리기사_요약노트.pdf", "parser_version": "3.x" },
  "topics": [
    {
      "seq": 6, "title": "7. SQL문 활용",
      "segments": [
        {
          "seq": 21, "page_from": 13, "page_to": 13,
          "content": "GROUP BY 절은 레코드를 특정 필드 기준으로 그룹화한다. HAVING 절은 …",
          "sentences": [
            { "seq": 0, "char_start": 0,  "char_end": 31 },
            { "seq": 1, "char_start": 32, "char_end": 68 }
          ],
          "figures": [ { "page": 13, "char_offset": 210, "needs_vision": true } ]
        }
      ],
      "concepts": [
        { "id": "…", "name": "HAVING",
          "definition": "그룹화된 결과에 조건을 지정하는 절",
          "segment_seqs": [21] }
      ]
    }
  ]
}
```

- 단원(topic) 안에 조각(segment)들이 들어 있고, 조각 안에 문장 위치(`char_start`~`char_end`)와 그림 정보가 있습니다.
- 개념은 단원에 붙어 있고, `segment_seqs`로 "이 개념이 어느 조각에 나오는지"를 가리킵니다.
- `needs_vision: true`인 그림 근처 문장은 출제에서 제외하는 데 씁니다.

## 2단계. 문제 만들기 시작

시작하는 문은 두 개입니다.

**① 자동 (기본)** — 자료 분석이 끝나는 순간 자동으로 시작됩니다. 이 자료가 담긴 과목(코스)이 없으면 자료 1개짜리 과목도 자동으로 만들어줍니다.

**② 수동 — "새 문제 만들기" (리필)** — 문제를 다 푼 사용자가 결과 화면에서 버튼을 누르면, **기존 문제는 그대로 두고 새 문제만 추가**로 만듭니다.

두 경우 모두 요청만 바로 받아두고 실제 생성은 백그라운드에서 진행합니다(몇 분 걸림). 같은 자료로 동시에 두 번 만드는 건 자동 차단됩니다.

**예시** — 작업 상태의 변화 (화면이 몇 초마다 확인하는 값):

```
요청 직후:  { 상태: "running" }                      → 화면: "새 문제를 만들고 있어요"
7분 뒤:     { 상태: "done", 저장: 21, 폐기: 35개 사유 목록 } → 화면: "새 문제 21개가 추가됐어요"
실패 시:    { 상태: "failed", 오류: "…" }             → 화면: "생성에 실패했어요"
```

## 3단계. 재료를 생성기 입력 형태로 변환

파싱이 데이터베이스 여러 테이블에 나눠 저장해 둔 결과를, 문제 생성기가 쓰는 **하나의 정해진 입력 묶음**으로 옮겨 담습니다. 이후 단계는 파싱이 내부적으로 어떻게 동작하는지 몰라도 되고, 이 묶음의 형태만 알면 됩니다 — 파싱 쪽이 바뀌어도 이 변환만 맞추면 문제 생성은 그대로 돌아갑니다.

파싱과 문제 생성은 같은 것을 다른 이름·다른 구조로 부릅니다. 이 단계가 그 사이를 잇습니다:

| 파싱이 주는 것 (1단계 예시의 트리) | 문제 생성기가 쓰는 것 | 비고 |
|---|---|---|
| `topics[]` (단원) | `tocs[]` (목차) | |
| `topics[].segments[]` (조각) | `chunks[]` | 단원 안에 있던 조각들을 한 줄로 폄 |
| `segments[].seq` | `chunks[].index` | 조각 번호 |
| `segments[].content` | `chunks[].raw_text` | 원문 텍스트 |
| `sentences[].char_start/char_end` | `sentences[].start/end` | 문장 위치 |
| `topics[].concepts[]` + `segment_seqs` | `chunks[].concepts[]` | 단원에 붙어 있던 개념을 **각 조각 안으로** 배분 |
| `figures[].char_offset` | `figures[].offset` | 그림 위치 |

**예시** — 변환 후, 생성기가 받는 입력 묶음:

```json
{
  "tocs":   [ { "index": 6, "title": "7. SQL문 활용", "chunk_indexes": [21, 22] } ],
  "chunks": [ {
      "index": 21, "page_from": 13, "page_to": 13,
      "raw_text": "GROUP BY 절은 레코드를 … HAVING 절은 … 조건을 지정한다. …",
      "sentences": [ { "start": 0, "end": 31 }, { "start": 32, "end": 68 } ],
      "concepts":  [ { "name": "HAVING", "definition": "그룹화된 결과에 조건을 지정하는 절" } ],
      "figures":   [ { "page": 13, "offset": 210, "needs_vision": true } ]
  } ]
}
```

한 개념이 여러 조각에 걸쳐 있으면 그 조각들 모두에 넣습니다(중복 출제 방지는 6단계 계획이 처리). 목차에 배정되지 않은 조각은 문제를 귀속시킬 단원이 없으므로 여기서 제외합니다.

## 4단계. 재료 이상 없는지 확인

| | |
|---|---|
| 들어오는 것 | 3단계의 입력 묶음 |
| 하는 일 | 아래 점검표를 위에서부터 전부 검사 (AI·데이터베이스 없이 코드만으로, 몇 초면 끝) |
| 나가는 것 | **오류**가 하나라도 있으면 전체 중단 + 보고서 / **경고**뿐이면 보고서에 기록만 하고 다음 단계로 진행 |

뒤 단계들이 전부 문장 위치를 믿고 동작하기 때문에("32~68번째 글자가 근거 문장이다"), 어긋난 재료는 초입에서 걸러냅니다. 검사 결과는 두 등급으로 나뉩니다 — **오류**(뒤 단계가 성립할 수 없음 → 즉시 전체 중단)와 **경고**(진행은 가능하지만 품질이 의심됨 → 기록만).

**점검표**:

| # | 확인하는 것 | 어긋나면 |
|---|---|---|
| 1 | 파싱 결과의 버전이 지원하는 버전인가 (지원 목록을 지정해 둔 경우만) | **오류** — 데이터 구조 자체를 믿을 수 없으므로 나머지 검사도 생략하고 즉시 중단 |
| 2 | 목차가 가리키는 조각이 실제로 존재하는가 | **오류** — 없는 조각이면 문제를 귀속시킬 단원이 없음 |
| 3 | 한 조각이 두 단원 이상에 중복 배정되지 않았는가 | **오류** — 단원별 출제량이 이중으로 계산됨 |
| 4 | 원문이 있는 조각에 문장 위치가 1개 이상 있는가 | **오류** — 문장 위치가 0개면 근거 지정 자체가 불가능. (예전엔 이 경우 검사를 통째로 건너뛰어 "통과"로 보이는 사고가 실측으로 확인됐고, 그 뒤 오류로 승격) |
| 5 | 각 문장 위치가 원문 범위 안인가 (0 ≤ 시작 < 끝 ≤ 원문 길이) | **오류** — 벗어난 위치로 문장을 자르면 엉뚱한 근거가 붙음 |
| 6 | 문장이 앞 문장과 겹치지 않는가 | 경고 — 같은 글자가 두 문장에 속해 근거 표시가 이중이 될 수 있음 |
| 7 | 문장 위치가 원문 끝 근처까지 (95% 이상) 이어지는가 | 경고 — 뒷부분 문장이 누락됐을 가능성 (그 부분은 출제 불가) |
| 8 | 그림 위치가 원문 범위 안인가 | 경고 — "그림 근처 문장 제외" 판단이 부정확해질 수 있음 |

**예시** — 오류로 중단되는 경우들 (점검 2·3·5):

```
"목차 6이 존재하지 않는 조각 #99를 참조합니다"      → 목차-조각 연결 오류
"조각 #21이 목차 5와 6에 중복 배정되었습니다"        → 한 조각이 두 단원에 소속
"조각 #21의 문장 위치(32~900)가 원문 길이(500자)를 벗어납니다" → 위치 정보 손상
```

오류 보고서는 파싱 파트에 그대로 전달해서 원인을 고치게 합니다. 경고는 중단 없이 생성 결과 보고서에 함께 실립니다.

## 5단계. 출제할 개념 고르기

| | |
|---|---|
| 들어오는 것 | 조각 (원문 + 문장 위치 + 개념 목록) |
| 하는 일 | 개념마다 "이 개념을 제대로 설명하는 문장"을 원문에서 찾는다 |
| 나가는 것 | 개념별 근거 문장 후보 / 못 찾은 개념은 사유와 함께 출제 제외 |

**예시** — 조각 21번의 개념 7개를 처리한 결과:

```
✅ HAVING     → 근거 후보: 1번 문장 ("HAVING 절은 … 조건을 지정한다")
✅ GROUP BY   → 근거 후보: 0번 문장
❌ 정규화      → 제외: "원문에서 근거 문장을 찾지 못함"
              (개념 목록엔 있지만 이 조각 문장 어디에도 설명이 없음)
❌ ER 다이어그램 → 제외: "근거 문장이 전부 그림 안에 있음"
              (그림 없이는 성립 안 되는 문장이라 텍스트 문제로 낼 수 없음)
```

여기서 제외된 개념은 문제가 안 만들어지고, 제외 사유는 생성 결과 보고서에 남습니다.

## 6단계. 출제 계획 세우기

AI 없이 정해진 규칙으로 계산합니다 — 같은 자료면 항상 같은 계획이 나옵니다.

| | |
|---|---|
| 들어오는 것 | 5단계의 조각별 선별 결과 — 조각마다 "출제 가능 개념 + 그 개념의 근거 문장 번호들" |
| 하는 일 | ① 단원별 문제 수(예산) 결정 ② 개념별 문항 수·유형(객관식/OX/단답형/빈칸) 배분 |
| 나가는 것 | 조각별 작업 지시서 — 7단계 AI 호출 1번당 1장 |

**5단계에서 넘어오는 모양** — 4단계까지 쓰던 "입력 묶음" 전체가 아니라, 5단계가 조각마다 추려낸 선별 결과만 받습니다:

```
조각 21번의 선별 결과:
  HAVING   → 근거 문장 번호 [1]
  GROUP BY → 근거 문장 번호 [0]
  (정규화·ER 다이어그램은 5단계에서 이미 제외됐으므로 여기로 안 넘어옴)
```

같은 개념이 여러 조각에 들어 있으면(3단계에서 예고한 중복), 여기서 **근거 문장이 가장 많은 조각 하나만** 그 개념의 출제 자리로 채택합니다 — 같은 개념 문제가 단원 안에서 두 번 만들어지는 걸 막는 장치입니다.

**① 단원별 몇 문제? — 예산 공식**

```
예산 = 출제 가능 개념 수 × 1.5     ← 계수
       단, 15문항보다 작으면 15로   ← 하한
           80문항보다 크면 80으로   ← 상한
최종  = 예산 × 1.15 (과생성)       ← 9단계 검증 탈락을 미리 대비해 15% 더 만듦
```

- **계수 1.5** — 개념 하나당 1문제만 만들면 중요한 개념도 딱 1개뿐입니다. 평균 1.5개꼴로 잡아, 중요한 개념에 여분이 돌아가게 합니다.
- **하한 15** — 개념이 몇 개 없는 단원(예: 개념 4개 × 1.5 = 6)도 최소 15문항은 시도합니다. 사용자가 한 단원만 골라 풀 때 문제가 너무 적지 않게 하기 위해서입니다.
- **상한 80** — 개념이 수백 개인 대형 단원이 AI 호출 비용과 생성 시간을 폭주시키지 않게 막는 뚜껑입니다.

**개념별로는 몇 개씩?** 예산을 이 순서로 나눕니다:

1. 모든 개념에 일단 1문제씩 — 커버리지 바닥 (어떤 개념도 통째로 빠지지 않게)
2. 예산이 남으면 **중요도 순**으로 한 바퀴씩 1개씩 추가 — 개념당 **최대 3개**까지
3. 반대로 개념이 예산보다 많으면 중요도 상위부터 배정하고, 밀린 개념은 이번 생성에서 제외

중요도 점수 = 기출에 자주 나온 개념(가장 큰 가중치) > 여러 조각에 반복 등장 > 다른 개념들이 선수 지식으로 참조.

**② 어떤 유형?** 근거 문장의 생김새(형태)로 후보를 정합니다: 정의 설명 → 단답형·객관식·OX / "A, B, C 세 가지" 나열 → 객관식 / "A → B → C" 절차 → 빈칸·객관식 / "반면에 ~" 비교 → OX·객관식. 후보가 여럿이면 단원 전체 유형 비율(객관식 40% · 빈칸 25% · 단답형 25% · OX 10%)에서 가장 모자란 유형부터 채우고, 같은 개념에 같은 유형을 두 번 내지는 않습니다.

**예시** — 단원 "7. SQL문 활용"의 계획:

```
출제 가능 개념 7개
  7 × 1.5 = 10.5 → 하한 15에 못 미침 → 예산 15문항
  15 × 1.15 = 17.25 → 최종 17문항 생성 시도

개념별 배분 (중요도: HAVING > GROUP BY > … 순이라고 가정):
  1바퀴: 7개 개념 전부 1문제씩            (7개 배정, 10개 남음)
  2바퀴: 7개 개념 전부 2문제째            (14개 배정, 3개 남음)
  3바퀴: 중요도 상위 3개만 3문제째         (17개 배정, 끝 — 개념당 상한 3 도달)

조각 21번 작업 지시서:
- HAVING   (정의형) → 단답형·객관식·OX 각 1개 · 근거 후보: 1번 문장
- GROUP BY (정의형) → 단답형·객관식·OX 각 1개 · 근거 후보: 0번 문장
- …
```

## 7단계. AI가 문제 만들기 ★

조각 하나마다 AI(솔라)를 한 번씩 호출합니다.

| | |
|---|---|
| 들어오는 것 | 조각 원문(문장 번호 붙임) + 작업 지시서 |
| 하는 일 | 아래 지시문으로 AI 호출 1번 (답을 못 읽으면 1번 재시도) |
| 나가는 것 | 문제 후보 목록 (아직 검증 전) |

AI에게 주는 지시문의 구조:

> **너는 시험 출제자다. 아래 원문만을 근거로 문제를 만들어라.**
>
> **[원문 문장 목록]** — 조각의 문장들에 번호를 붙여 나열
> **[출제 지시]** — 6단계의 작업 지시서 (개념·유형·근거 문장)
> **[유형별 작성법]** — 객관식은 선지 4개 + 오답마다 "왜 아닌지", 단답형 정답은 짧은 용어만, 빈칸 문제는 문장과 용어만 고르면 됨(지문은 시스템이 만듦) 등
>
> **[지키지 않으면 그 문제는 자동 폐기되는 약속]**
> 1. 정답은 근거 문장만으로 입증돼야 한다 — 원문에 없는 사실 금지
> 2. 정답은 자동 채점이 가능해야 한다 — 짧은 용어만, 긴 서술 금지
> 3. 원문 표기를 그대로 쓰되, 입력하기 어려운 기호는 대체 표기도 함께
> 4. 시험 문체로 쓴다 — "~입니다", "~인가요?" 같은 말투 금지
> 5. 내부 문장 번호를 문제에 노출하지 마라
> 6. 정답은 하나뿐이어야 한다 — 오답 선지가 원문 어디에서도 정답이 되면 안 됨
> 7. 못 만들겠으면 건너뛰어라 — 억지 문제보다 적은 문제가 낫다
>
> **[모범 답안 예시]** — 형식만 따라 하라 (내용 복사 금지)

경험상 "하지 마라" 목록을 늘리는 것보다 **잘 만든 예시를 보여주는 것**이 훨씬 효과가 컸습니다 (실측으로 저장량 2.5배). 기출 PDF를 올린 과목은 "이 시험은 이런 말투로 낸다"는 발문 예시도 추가됩니다.

**예시** — AI가 돌려주는 문제 후보 하나:

```json
{
  "type": "shortAnswer",
  "concept": "HAVING",
  "data": {
    "prompt": "GROUP BY로 그룹화된 결과에 조건을 지정하는 절은 무엇인가?",
    "accepted": ["HAVING", "HAVING 절"],
    "explanation": "HAVING 절은 그룹화된 결과에 조건을 지정한다."
  },
  "evidence": ["s1"],
  "difficulty": 2
}
```

## 8단계. 기본 점검

AI 답변을 받자마자 코드가 먼저 거릅니다.

| 점검 | 예시 |
|---|---|
| 빈칸 문제는 코드가 완성 | AI는 "1번 문장에서 'HAVING'을 빈칸으로"만 정함 → 코드가 지문을 조립: "GROUP BY로 그룹화된 결과에 조건을 지정하는 것은 [____] 절이다" (AI에게 지문 작성을 맡기면 정답이 지문에 남는 사고가 나서) |
| 근거 문장이 실존하는가 | 근거가 "9번 문장"인데 조각에 문장이 5개뿐 → 폐기 |
| 근거가 계획 범위 안인가 | 작업 지시서는 1번 문장을 줬는데 AI가 3번 문장을 근거로 씀 → 폐기 (엉뚱한 근거 차단) |

## 10단계. 저장

| | |
|---|---|
| 들어오는 것 | 검증에 합격한 문제들 |
| 하는 일 | 중복 제거 후 데이터베이스 `quiz_items` 테이블에 저장 |
| 나가는 것 | 과목 카드의 문항 수 갱신 ("생성 중" → "N문항") |

- **어디에 저장되나**: PostgreSQL의 `quiz_items` 테이블. 문제 1개 = 1행.
- **중복 방지**: 질문 내용이 (띄어쓰기 차이만 빼고) 같으면 하나만 남깁니다. 리필일 때는 기존 문제들과도 대조합니다.
- **탈락한 문제**: 저장하지 않고, "어느 단계에서 왜 떨어졌는지"만 생성 결과 보고서에 남깁니다.

**예시** — 저장되는 행 하나:

| 컬럼 | 값 |
|---|---|
| course_id / document_id | 어느 과목·어느 자료의 문제인지 |
| toc_index / toc_title | 6 / "7. SQL문 활용" — 단원 귀속 |
| type | shortAnswer |
| concept_name | HAVING |
| data | 문제 내용 전체 (질문·정답·인정 표기·해설) |
| evidence | 근거 원문 텍스트 + 교재 쪽수 — 풀이 화면의 📎 박스가 이걸 보여줌 |
| verified | true (검증 통과 표시 — 이 값이 true인 문제만 출제됨) |
| created_at | 저장 시각 |

## 11단계. 사용자가 문제를 푼다

| | |
|---|---|
| 들어오는 것 | 범위(단원들) + 문항 수 + **이 브라우저에서 이미 푼 문제 목록** |
| 하는 일 | 안 푼 문제 우선으로 뽑고, 모자라면 오래전에 푼 것부터 복습으로 채움. 정답·해설은 빼고 보냄 |
| 나가는 것 | 문제 목록 + 복습 개수 |

**예시** — 세션 요청과 응답:

```
요청:  단원 [6], 10문항, 이미 푼 문제 5개의 번호 목록
서버:  이 범위에 문제 12개 → 안 푼 것 7개 전부 + 복습 3개(푼 지 가장 오래된 순)
응답:  { 문제 10개(정답 없음), recycled: 3 }
       → 화면: 뒤쪽 3문제에 🔄 복습 표시, 시작할 때 "복습 3문항 포함" 안내
```

**채점** — 답을 제출하면 그때 서버가 채점하고, 정답·해설·📎 근거 원문을 처음으로 내려보냅니다:

```
제출: "having"        → 정답 (대소문자·띄어쓰기 무시)
제출: "HAVING 절"     → 정답 (인정 표기 목록에 있음)
제출: "GROUP BY"      → 오답 — "정답은 HAVING" + 해설 + 교재 13쪽 근거 문장 표시
```

정답은 서버만 알고 있으므로 화면 소스를 뒤져도 답이 보이지 않습니다.
