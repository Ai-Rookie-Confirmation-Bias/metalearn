# WORK_LOG — feat/curriculum (학습 커리큘럼 엔진)

담당 **윤현석**. dev에서 분기해 학습 페이지(커리큘럼)를 새로 만든다.
integration 코드는 **참고만** 하고 가져오지 않는다 — 그쪽 파싱에 맞춘 모양이라 지금과 다르다.
다만 그쪽이 이미 부딪힌 벽(전체 문서 1콜 → 커버리지 부족, 학습을 잠갔더니 이탈,
락 잡은 채 LLM await)은 계속 참고한다.

**새 블록은 맨 위에 붙인다.** 자세한 건 `git log`(커밋 메시지에 실측 숫자까지 있다).

**블록에 꼭 넣을 것 — 커밋에 안 남는 것들.**
코드는 `git log`가 갖는다. 워크로그가 아니면 사라지는 건 이것들이다.
```
정한 것    대화에서 결정된 방향. 왜 그렇게 정했는지 한 줄
뒤집은 것  전에 맞다고 했다가 틀린 것으로 판명된 판단. **이게 제일 중요하다** —
           안 적으면 다음 세션이 같은 길을 다시 간다
기각한 것  검토했다가 안 하기로 한 것. "이렇게 하면 되지 않나"를 미리 막는다
```

⚠️ **WORK_LOG 커밋은 기능 커밋과 섞지 않는다.** 세션 끝에 하나씩, 별도로.
통합 머지는 **기능 커밋까지만** 가져간다(7/11에 딸려 들어간 사고 후 만든 규칙).

### 정한 것

- **학습 화면은 개념 단위 묶음**([설명 · 그림 · 그 개념 빈칸]). 자르는 규칙은

- **분석은 내 자료만 센다.** 기본 제공이 분모에 들어가 내 182화면이 336이 됐다.

### 기각한 것

- **시연 영상용 목업 데이터.** "야매로 만들어 바로 내자"는 요청이 있었으나, 실제로

→ 다음에 "A 지시가 B 지시를 눌렀다"는 가설이 서면 **B를 빼고 먼저 돌려 봐라.**

→ 한 칸만 보는 검증은 검증이 아니다.

- **무엇을 지킬지는 형식이 정한다**(`profile._ENFORCE`). 분량 지시 쪽에

  비유가 붙었다(2/4 오염).
- 촬영용 시드는 **뒤 목차에** 넣는다(`demo_seed --from-chapter`). 앞부터

  ("데모용으로 사이클이 다 돌아가게, 너무 완성도를 높이려고 하지 말고")

## 2026-08-08 · 세 갈래 병합 · 진단 화면 · 메타인지 분석 — 백엔드가 아니라 화면이 남아 있었다

`feat/course-to-curriculum`(박지성)을 합치고, 그쪽이 다 만들어 둔 24번 API를 부를
화면과 메타인지 분석을 붙였다. 커밋 셋(분석 API → 진단 화면 → 분석 화면).

### 정한 것
- ★ **코스에도 주인이 있다.** `courses.user_id`가 `users.id` FK다 — 자료를 사람별로
  가른 이유가 코스에 그대로 적용된다. `sync_courses`에도 `user_id`를 걸었다.
  안 걸면 남의 수업이 내 책장에 뜬다
- ★ **책장 = (픽스처 + 내 자료 + 내 코스) − 내 코스에 묶인 자료.** 두 번째 필터가
  이번 병합의 판단 자리다. 박지성 쪽은 사용자 개념이 없어 **코스에 묶인 자료를
  전부** 뺐는데, 자료는 설계상 공용이라 그러면 **남이 자기 수업에 넣었다는 이유로
  내 책장에서 자료가 사라진다.** `course_member_document_ids(user_id=…)`로 좁혔다
- **분석 API는 계산을 안 한다.** `summarize()`가 자료별로 이미 다 낸다. 여기가 하는
  일은 모아서 **화면 수로 가중**하는 것뿐 — 단순 평균이면 3화면 샘플이 124화면
  교재와 같은 무게가 돼 준비도가 샘플에 끌려간다. **분량이 곧 비중이다**
- ★ **빈 출처를 감추지 않는다.** `byKind`가 0인 출처에 경고를 띄운다 —
  *"그만큼 준비도의 근거가 얇습니다."* 0을 숨기면 화면이 실제보다 튼튼해 보이고,
  그건 이 화면이 하려는 말과 정반대다. 실측이 `{retrieval: 4}` 하나뿐이라
  **이 결정이 곧 화면의 절반**이었다
- **화면이 등급을 매기거나 평균을 내지 않는다.** 그러면 "왜 이 숫자인지"를 두 곳에서
  찾아야 한다. 가중치 표기(×0.5~×2.0)만 화면에 적고, `mastery.WEIGHT`와 같아야 하는
  값이라 주석으로 묶었다
- **진단 ③ 문구는 "어떤 설명이 읽기 편한가"다.** "당신에게 맞는 학습법"이 아니다.
  러닝 스타일 맞춤에 학습 효과 근거가 없다(Pashler 2008) — 이건 성취가 아니라
  이탈을 막는 장치다. 박지성님 설계 메모 그대로 따랐다
- alembic `0009_diagnostic` → `0010`으로 내렸다. **0009가 두 번째 충돌이다**

### 뒤집은 것 ★
- ★ **문서에 예측값을 먼저 적었다.** 병합 문서에 `297 passed`·`43경로`로 써 놨는데
  실측은 `294`·`42경로`였다. 코드는 합쳐졌는데 **숫자는 안 합쳐졌다** — 병합이면

  ⇒ **문서 숫자는 예측하지 않는다. 재서 적는다.** 두 세션 연속 같은 실수다
- ★ **내 편집이 엉뚱한 함수에 들어갔다.** `_my_doc_ids`가 자기 자신을 부르고 있었다 —

  증상은 리로드 중 로그에 섞여 **재귀라는 것도, 지점도 안 보였다.**
  ⇒ 같은 이름의 로직을 두 자리에 옮겨 심을 땐 **함수 목록부터 다시 뽑아 볼 것**
- **마크다운 카드가 깨졌을 때 데이터부터 의심했다.** ③ "표로 비교" 카드가 원문

  이번엔 렌더가 범인이었다

## 2026-08-08 · 코스 만드는 자리 — 파일 N장 → 수업 한 권

`/create`가 파일만 올리고 끝내던 자리를 `POST /api/courses`까지 이었다.
목록 API(`GET /api/courses`)도 같이 열었다 — 문제집이 `course_id`를 고를 문이다.

### 정한 것
- ★ **ready 전에 코스를 만들지 않는다.** 역할 제안이 밀도에, 목차 복사가
  `doc_topics`에 기대므로. 위저드는 의도를 localStorage에 남기고, 책장이 폴링하다
  전부 ready면 그때 `POST`한다
- **roles는 안 보낸다.** 메인/추가 ≠ skeleton/body/reference — 두 세션 연속 같은
  기각. 서버 `suggest_roles`에 맡긴다
- **purpose는 진단 goal로만 매핑**한다(`exam/career/culture|hobby` →
  `exam/work/interest`). 코스 바디에 purpose 칸이 없다
- 책장 카드는 자료 N장이 아니라 **"수업 준비 중" 한 장**이다. 개별 ready 자료가
  책으로 잠깐 뜨면 코스 생성 직후 멤버 제외로 사라지며 깜빡인다
- `ensure_topics`는 안전망이다 — curl이 너무 일찍 만들어도 tree/sync 때 목차를
  채운다. **역할은 다시 안 고친다**(REFERENCE로 굳은 본문을 BODY로 올리지 않음)

### 뒤집은 것 ★
- **"생성하기 = 즉시 POST"가 틀렸다.** 접수증만 있으면 문서는 있지만 밀도·목차가
  없다. 그 상태로 만들면 topics=0 · 비-뼈대는 REFERENCE로 굳는다

### 검증 숫자
```
GET /api/courses          목록 동작 (실측 2)
POST → 책장               멤버 자료 숨김 · 코스 id 등장 · topics 4
tsc / pytest              통과 (294)
```

### 아직 안 된 것
- 문제집 화면이 여전히 mock — 이제 `course_id`를 받을 준비는 됐다
- 위저드에서 자료 형태(교재/슬라이드)를 고르지만 서버로 안 간다. 밀도·형식이 정한다

## 2026-08-07 · 로그인(OAuth) 이식 · 내 책장 — "내 것"이 없던 걸 만든다

`feat/oauth-login`의 인증 코드를 가져오고, 이어서 업로드·책장·진도를 사람별로 갈랐다.
커밋 둘로 나눴다(로그인 → 확인 → 소유 분리).

### 정한 것
- **머지가 아니라 파일 이식.** 저쪽 auth 코드는 완성 상태인데 alembic 계보가 갈린다 —
  `0020_oauth_user`가 **이미 있는 users에 컬럼을 붙이는** 마이그레이션이고 이쪽엔
  users가 아예 없다. 브랜치를 합치면 스키마가 통째로 충돌한다.
  파이썬/TS만 옮기고 `0009_users`를 **최종 모양(생성+컬럼)으로 한 번에** 새로 썼다
- **폴백을 남긴다.** Bearer > X-User-Id > dev 유저. 로그인 붙였다고 기존 화면이
  전부 401이 되면 데모가 통째로 멈춘다. 단 **깨진 토큰은 401이다** — 조용히 dev로
  떨어지면 만료 토큰을 든 사람이 남의 자료를 본다
- **미설정 제공자는 화면에서 잠근다.** 네이버 자격증명이 비어 있어 그대로 두면
  눌렀을 때 503만 돌아온다. `GET /api/auth/providers`를 새로 만들어 근거로 삼았다
  (저쪽엔 없던 것 — 저쪽은 트라이얼이라 둘 다 채워져 있었다)
- **콜백 실패는 302다.** 사용자는 브라우저로 거기 도착해 있다. JSON 에러를 던지면
  흰 화면에 detail만 남는다. `#error=…`로 보내고 프론트가 문장으로 바꾼다
- **픽스처는 공용으로 둔다.** DB 행이 없는 데모 자료라 소유를 붙일 자리가 없고,
  붙였다면 새 계정으로 처음 들어온 사람이 빈 화면만 본다
- **진도 스냅샷을 사람별 파일로 나눈다**(`data/progress/{user_id}.json`).
  예전 단일 파일은 서버가 뜰 때 dev 유저 몫으로 한 번 옮긴다 — 안 옮기면
  그동안 쌓인 진도가 로그인 붙이는 순간 사라져 보인다
- **FK를 지금 건다.** `courses.user_id`·`user_documents.user_id` 둘 다 0행이라
  지금이 제일 싸다. `docs/STATUS.md` §5의 "users가 없어 FK를 못 걸고 있다"가 닫힌다

### 뒤집은 것 ★
- **"업로드에 소유를 붙이는 건 새 기능"이 틀렸다.** `ParsingService.register`는
  **이미 `user_id`를 받아 `link_user`까지 하도록 돼 있었고 라우터만 안 넘기고 있었다.**
  파싱→문제은행, 파싱→업로드에 이어 **세 번째로 같은 모양이다: 없던 건 기능이 아니라
  인자 하나였다.** 이 브랜치에서 "안 된다"는 말은 일단 호출부부터 의심할 것
- **passlib을 pyproject에 남겨둘 뻔했다.** bcrypt를 끌어오니 그대로 둬도 된다고
  봤는데, 그러면 "왜 bcrypt를 직접 부르나"의 답이 코드 어디에도 없다. 선언을
  `bcrypt>=4.1`로 바꾸고 이유를 주석에 붙였다(passlib 1.7.4가 bcrypt 4.1+에서
  버전 탐지가 깨져 **해싱 자체가 실패한다**. 이 브랜치가 그 깨지는 코드였다)
- **FK를 걸고 나서야 X-User-Id의 구멍이 보였다.** 아무 UUID나 넣으면 읽기는
  멀쩡한데 **소유를 남기는 순간 업로드가 500으로 죽는다**(ForeignKeyViolation,
  원인은 컨테이너 로그에만). 스모크에서 빈 응답으로 잡혔다.
  쓰는 자리마다 막는 대신 `get_current_user_id`가 실재 계정인지 한 번 확인한다 —
  유령 id 400, 지워진 계정의 토큰 401. **FK는 제약이 아니라 검출기였다**

### 기각한 것
- 저쪽 `llmApiClient`(180초 인스턴스) 이식 → 이 브랜치는 호출부마다 timeout을 준다.
  느린 API가 생길 때마다 인스턴스를 늘리면 어느 걸 써야 하는지가 호출부의 판단이 된다
- 저쪽 `0020` 마이그레이션 그대로 쓰기 → 있지도 않은 테이블에 컬럼을 붙인다
- 위저드의 메인/추가를 `role`로 보내기 → 서버 역할은 뼈대/본문/참고라 **축이 다르다.**
  임의로 짝지으면 사용자가 고르지 않은 값이 저장된다(안 보내는 것보다 나쁘다)
- 딥링크로 남의 문서 열기를 막기 → 문서는 설계상 공용이고 진도는 이미 갈렸다.
  막으면 픽스처 딥링크까지 같이 죽는다
- `store.documents`를 그대로 책장으로 쓰기 → store는 서버가 지금까지 읽은 자료
  **전부**라 남이 올린 것이 섞인다. 소유는 매번 DB에서 다시 센다

## 2026-08-07 · 업로드 화면 — 데모 첫 장면을 화면으로

`POST /api/parsing/documents`를 부르는 화면이 없어 curl로 올리던 것을 이었다.
책장 → **새로운 학습 시작하기**(`/create`) → 파일 고름 → 책장에 "분석 중" 카드 →
ready가 되면 책 카드.

### 정한 것
- 파일은 **고르는 순간 올린다.** 마지막에 몰아 올리면 사용자가 목표를 고르는
  동안 파싱이 놀고 있다. 파이프라인이 분 단위라 그 시간이 그대로 대기시간이 된다
- 진행 상태는 **서버에서만 온다.** Zustand가 드는 건 "책장이 아직 모르는 문서 id"뿐이고
  (원칙 3) 단계 문구·진행 막대는 서버 `DocStatus`를 표에서 찾은 값이다.
  화면이 시간을 재거나 단계를 추측하지 않는다
- 대기 목록은 **localStorage에 남긴다.** 분 단위 파싱 도중 새로고침은 실제로 일어나고,
  안 남기면 방금 올린 자료가 책장에서 통째로 사라져 보인다
- 대기 카드는 **책장 목록이 그 자료를 알아본 뒤에** 뺀다. ready 즉시 빼면 카드가
  한 번 사라졌다 다시 나타난다(목록 API가 sync를 해야 자료가 보인다)
- `role`은 **안 보낸다.** 서버가 그 값을 user_documents에만 쓰는데 user_id가 없으면
  아예 저장되지 않는다. 반영도 안 되는 값을 보내면 "역할을 정했다"는 착각만 남는다

### 뒤집은 것 ★
- **"업로드 화면이 없다"가 정확히는 틀렸다.** 위저드는 `/create`에 라우트까지 붙어
  있었고 책장 빈 화면도 거기로 보내고 있었다. 없던 건 화면이 아니라 **POST 한 줄**이다.
  → 파싱→문제은행 때와 같은 모양이다: **없던 건 데이터가 아니라 출구였다.**
  "화면 없음"으로 적어두면 다음 사람이 화면부터 새로 그린다
- **`course-create/store.ts`는 대역이 아니라 걸림돌이었다.** `setTimeout` 3초로
  "생성 중 → 완료"를 흉내내고 있어서, 진짜 상태를 붙이려면 지우는 게 먼저다.
  스토어 주석이 스스로 "백엔드 붙으면 제거"라고 적어둔 대로 지웠다

### 기각한 것
- 링크·텍스트 자료 입력 → 서버에 받는 문이 없다. 고를 수 있게 두면 **제출할 수 없는
  행**이 목록에 남는다. UI만 있고 배관이 없는 게 이번에 고친 문제와 같은 종류다
- 파싱 쪽에 문서 목록 API 추가 → 소유 경계(전과 같은 판단). 대기 목록은 클라가 든다
- 업로드 직후 `POST /curriculum/documents/from-parsing/{id}` 호출 → 목록 API가 이미
  sync한다. 두 곳에서 주입하면 언제 들어갔는지가 두 갈래가 된다

### 정한 것
- ★ **오측정이 미측정보다 나쁘다.** 게이트가 `concept` 라벨 개수만 잠그면

- "정의/상황"이라 신고했는데 답이 개념명이 아니면 폐기(이름 인출 위장)

### 뒤집은 것

### 검증에서 나온 것 (같은 세션, 다른 눈)

먼저 **잰 뒤에 판단했다.** 단위 테스트는 규칙이 의도대로 도는지만 잠근다 —
의도 자체가 틀렸는지는 실측이라야 나온다. 결함 둘 다 여기서 나왔다.

- ★ **같은 함수를 상대 크기가 다른 자리에 쓰면 안 된다.**
  `_answer_concept`에는 "표기가 조금 달라도 서로 **포함**이면 같게 본다"는 완화가
  있다. 상대가 이 화면 개념 두셋일 때는 맞다. 그대로 `foreign_keys`에 썼는데
  거긴 **문서 전체가 상대**다(실측 371개, 3자 이하가 59개).
  ```
  성질 정답 '이미 오름차순으로 정렬된 상태를 유지하는 배열의 일부'
      → 문서 어딘가의 개념 '상태'를 품었다는 이유로 폐기 (실제 생성물)
  정의문 377개를 정답이라 치고 재니 남의 개념으로 오인 117개 = 31%
      '모듈' ⊂ '모듈화'  ·  'WAS' ⊂ 'OWASP'  ·  '노드' ⊂ '단말 노드' (26쌍)
  ```
  ⇒ `_foreign_hit`으로 갈라 **정확 일치만** 본다. 잡아야 할 사고
  (`answer='XP(eXtreme Programming)'`)가 원래 그 모양이라 잃는 게 없다.
  **오폭 31% → 0%, 잡아야 할 것은 그대로 잡힘.**
- ★ **채점 귀속용 키와 측정용 라벨을 같은 칸에 두면 하나를 끌 때 둘 다 꺼진다.**
  성질 문항의 `concept_keys`를 비웠더니 `_levels_of`가 정의문을 못 찾고,
  `assess_cloze`가 "잴 수 없으면 강등 안 한다"로 L2를 준다. 결과적으로
  **정의문을 통째로 베낀 성질 문항이 L1 게이트를 그냥 통과한다.**
  ```
  scrub 전 [1]  →  scrub 후 [2]      (고치기 전, LLM 없이 재현됨)
  ```
  ⇒ 라벨을 `content.concept`에 남기고 `concept_keys`만 비운다. 객관식이 이미
  쓰던 방식이다. **워크로그에 이미 있던 원칙의 재발** — *원문 밖 정보는 필드를
  나눠라*(비유·tie_in). 같은 벽을 칸 이름만 바꿔 또 만났다
- 오폭은 **조용하다.** 문항이 하나 없어져도 화면은 멀쩡해 보이고 커버리지에도
  안 잡힌다(성질은 원래 안 세니까). 폐기에는 **사유별 카운트**가 있어야 한다 —
  이번엔 `scrub_blocks`를 감싸 밖에서 셌다(`bench/scrub_probe.py`)

```
20 근거 위치     ✅  tree의 concept에 evidence + global_key 추가. 부착률 99%
16 끊긴 고리     ✅  GET /courses/{id}/gaps — 교재 밖 선행 개념(박지성 몫)
13~15 코스 층    ✅  자료 여러 개 = 한 수업. 뼈대(PPT)/본문(교재) 역할
```
- 트리 스키마는 우리 픽스처와 **정확히 일치**한다(evidence 7필드·concept 8필드).
  어댑터는 안 깨진다
- ★ **lesson이 v3에도 없다.** 절 폐기의 근거였던 "의미 묶음은 파싱 몫"이 아직
  안 채워졌다. 폐기 유지는 맞다고 보지만("이유를 못 대는 판단은 부채"는 파싱
  일정과 무관하게 성립), **"lesson 오면 교체"는 무기한 대기로 읽어야 한다.**
  데모는 순수 슬라이싱으로 나간다

### 🔴 팀 회의 안건 — 커리큘럼 배분을 누가 하는가
STATUS 마지막 줄: *"`course_topics`에 `plan`(normal/skip/brief/deep)과
`origin`(book/inserted), `anchor_concept_id`를 미리 뒀다 — 24·27번이 채울 자리다."*
```
              파싱 쪽 (course_topics)        우리 쪽 (planner.py)
분량 배분     plan: normal/skip/brief/deep   mode: deep/normal/compressed
단원 삽입     origin: book/inserted          ❌ 안 한다(목차 고정이 서비스 원칙)
근거          24 진단 결과                    숙련도 누적(진단·인출·복습·형성)
```
**같은 일을 두 곳에서 하려 하고 있다.** 정해야 할 것:
- 배분을 파싱/코스 층에서 하면 우리 `planner.py`는 지우고 `plan`을 읽기만 한다
- 우리가 하면 파싱은 `plan` 칸을 비워 두고 진단 결과(`mastery_hint`)만 준다
- ⚠️ `origin: inserted`(단원 삽입)는 **우리 서비스 정의와 충돌한다** —
  목차는 고정이고 결손은 다음 설명에 녹인다고 정했다. 이것부터 맞춰야 한다

우리 입장 제안: **배분은 우리가 한다.** 근거가 숙련도 누적인데 그 데이터가
우리 쪽에만 있다(진단·인출·복습·형성 4출처). 파싱은 `mastery_hint`(22번)만
주면 우리가 첫 배분의 입력으로 쓴다.

### 형성평가 — 화면을 가로지르는가 (에이전트 4번째)
```
인출  화면 안    방금 읽은 글에서 꺼낸다      "결합도란?"
형성  화면 사이   가로질러 구별한다            "자료 결합도 vs 제어 결합도"
```
다르지 않으면 **인출 몰아보기**라 따로 만들 이유가 없다. 그래서 객관식이 주력이다 —
빈칸은 개념 하나를 꺼내는 것이라 구별을 못 재고 그건 이미 인출이 한다.

- **부탁하지 않고 잰다.** `crossing()` = 한 문항의 **보기에 서로 다른 화면 개념이
  둘 이상** 섞였는가. 순수 로직이라 모델의 "종합 문항입니다" 신고를 안 믿는다.
  `MIN_CROSS_RATIO=0.5` 미달이면 어느 문항이 왜 걸렸는지 붙여 한 번 다시 만든다
- **무엇을 물을지도 규칙이 고른다**(`select_concepts`). 단원에 개념 50개, 문항은
  5개다. LLM에 맡기면 매번 달라져 "왜 이걸 물었는지"를 못 쓴다
  ```
  1순위 자주 틀린 개념      약점을 확인 안 하는 평가는 평가가 아니다
  2순위 아직 안 풀어본 화면  미측정 자리. 숙련도에 구멍으로 남아 있다
  ```
- **기록은 정답 개념을 가진 화면에.** 문항은 가로지르지만 숙련도는 화면 단위다.
  어느 화면인지는 백엔드가 정해 `content.sectionId`로 보낸다 —
  프론트가 고르게 두면 화면이 판단을 하게 된다
- 실측(필기 1단원 29화면): 잠김 안내 → 진도 0.62에서 열림 →
  **문항 5개 · 가로지름 5/5 · 약점 5개 전부 확인**

### 정한 것 (형성평가)
- **잠금은 평가에만, 그리고 진도로만.** 학습은 절대 안 잠근다(integration이
  학습을 잠갔다가 이탈을 겪었다). **이해도로 잠그면 안 된다** — 못 하는 사람일수록
  확인할 기회가 사라져 도와야 할 사람에게서 도구를 뺏는다. `FORMATIVE_UNLOCK=0.6`

  알 수 없다. 목차 화면에 **입구는 잠겨도 보여준다** — 무엇을 향해 학습하는지가
  보여야 진도가 의미를 갖는다
- 캐시 키는 단원+약점. **진도는 안 넣는다** — 넣으면 화면 하나 볼 때마다 평가가
  새로 만들어져 열어놓고 푸는 도중에 문항이 바뀐다

  전부 `Attempt(kind, ...)`로 들어와 하나의 준비도가 된다
  ```
  준비도 = 이해도 × 진도 × 회상 강도
  ```
- **회상 강도**(망각곡선) — 마지막 성공 이후 감쇠. 반감기 3일에서 시작해

### 정한 것
- **약점은 절 단위로 짚는다.** 목차 단위로만 넘기면 목차 하나가 절 20개라 반영이
  20절 뒤에 나타난다. 학습자는 체감을 못 한다
- **이어지는 것만 녹인다.** 선수관계이거나 분류어를 공유할 때만
  (`자료 결합도`↔`제어 결합도`는 `결합도`를 공유). 실측(필기) 직전 절 개념을
  틀렸을 때 12/99에서만 판정 — **낮은 게 맞다.** 억지로 엮으면 설명이 산만해진다
- **출처마다 가중이 다르다** — 진단 0.5 · 인출 1.0 · 복습 1.5 · 형성 2.0.
  진단 오답은 **아직 안 배운 것**이지 무지의 증거가 아니다. 1.0을 주면 초반 오답이
  영원히 발목을 잡는다(`improving`을 만들 때 겪은 것과 같은 문제).
  복습 정답은 시간이 지나고도 꺼낸 것이라 훨씬 센 증거다
- **망각은 이해도를 안 깎는다.** 가만히 있는데 숫자가 내려가면 화면에서 설명할 수
  없다. `이해도`(안 떨어짐)와 `회상`(떨어짐)을 따로 두고 준비도에서 곱한다.
  `understanding`을 따로 내보내는 이유: 준비도가 낮은 게 **잊은 것**인지
  **아직 모르는 것**인지 갈라야 처방(복습 vs 다시 학습)이 나온다
- 판정 자격도 가중으로 (`MIN_ATTEMPTS 3회` → `MIN_WEIGHT 3.0`)

### 뒤집은 것
- **"약점 문단을 설명 본문 안에 넣어라"는 안 먹힌다.** 처음엔 프롬프트에
  `🔍 여기서 잠깐 —`으로 시작하는 문단을 본문에 넣으라고 했다. 관련 있는 절에서도
  **0회**였다(본문 318자로 짧게 쓰며 밀어냄). **비유를 별도 필드로 뺐을 때와
  같은 문제** — 학습자 이력에서 온 정보라 "원문 사실만 써라"와 프롬프트 안에서
  충돌하고, 모델은 안전한 쪽(안 씀)을 택한다. `tie_in` 별도 필드로 빼니 나온다.
  ⇒ **원문 밖 정보는 전부 필드를 나눠라.** 이걸로 두 번째다
- **"한 번도 못 맞힌 절도 복습 대상"** — 형성평가 오답 1건뿐인 절이 "복습 대기"로
  잡혔다(실측에서 발견). 그건 아직 모르는 것이라 처방이 다르다. 복습은 **맞힌 적
  있는데 잊혀가는 것**이다. `needs_review`에 `last_success` 조건을 걸었다
- **"DB가 없어서 누적이 안 된다"** — 윤현석 추정이었고 틀렸다. 인메모리에서도
  누적은 됐다(4문제 후 약점 개념 추출 확인). 원인은 배선 부재였다
- ★ **"인출 밀도를 개념 단위로 바꿔서 해결됐다"** — 아니었다(리뷰에서 잡힘).
  **단위만 바뀌고 강제가 없었다.** "빈칸은 개념마다 하나씩"이 프롬프트의 부탁으로만
  남아 있었고, 재시도 루프는 `l1_ratio`만 보고 `gap`은 계산해서 화면에 내보내기만
  했다. 14절 실측에서 재시도가 **한 번도 안 걸렸다**
  ```
                      전      후
    인출된 개념      39/48   47/48   81% → 98%
    빠짐 없는 절      6/14   13/14   43% → 93%
    개념당 빈칸       0.83    1.00
  ```
  → **품질과 누락은 처방이 다르다.** L1이 높으면 만드는 방식이 잘못된 것이라 전체를
  다시 만들어야 하고, 누락은 나머지가 멀쩡하므로 **그 개념만 다시 요청해 덧붙인다.**
  누락을 전체 재생성으로 고치면 잘 나온 문항까지 흔들린다(같은 절이 생성마다
  빈칸 1개↔5개로 출렁였다). 덧붙이기는 결과가 단조 증가한다
  → **범위를 좁혀 시켜야 한다.** 개념 10개 중 2개가 빠졌을 때 10개를 다시 시키면
  또 8개만 만든다. 2개만 시키면 2개를 만든다(`•4회전` 절: 빈칸 2 → 보충 8 → 10/10)
- ★ **"게이트로 인출이 해결됐다"** — **개수만** 해결됐다. 게이트가 `concept` **라벨**로
  세기 때문에 "라벨 ≠ 실제 묻는 것"이 그대로 통과한다. `0-8cdd5ac9` 4문항 중 2개:
  ```
  concept='애자일 모형'     answer='XP(eXtreme Programming)'  ← 다른 절 개념이 정답
  concept='프로토타입 모형'  answer='견본·시제품'              ← 성질 유형(의도)
  ```
  성질 유형은 프롬프트가 허용한 설계다(`※ 성질 유형의 answer는 예외`). 문제는
  **숙련도가 그걸 구분 없이 라벨 개념에 기록**한다는 것 — 성질 문항을 맞혀도
  "그 개념을 꺼낼 수 있다"의 증거는 약하다. ⇒ **미측정이 오측정으로 바뀔 수 있다.**
  정답이 **이 절 밖 개념**인 건 유형과 무관하게 그냥 사고다(XP 케이스)
  → 개념마다 상황·정의 유형 **최소 1개는 보장**하고 성질은 그 위에 추가.
    정답이 절 밖 개념이면 폐기. `retrieval_level`이 이미 유형을 판정하므로 재료는 있다
