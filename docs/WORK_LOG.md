integration 코드는 **참고만** 하고 가져오지 않는다 — 그쪽 파싱에 맞춘 모양이라 지금과 다르다.
다만 그쪽이 이미 부딪힌 벽(전체 문서 1콜 → 커버리지 부족, 학습을 잠갔더니 이탈,
락 잡은 채 LLM await)은 계속 참고한다.

**새 블록은 맨 위에 붙인다.** 자세한 건 `git log`(커밋 메시지에 실측 숫자까지 있다).

**블록에 꼭 넣을 것 — 커밋에 안 남는 것들.**
코드는 `git log`가 갖는다. 워크로그가 아니면 사라지는 건 이것들이다.
```

뒤집은 것  전에 맞다고 했다가 틀린 것으로 판명된 판단. **이게 제일 중요하다** —
           안 적으면 다음 세션이 같은 길을 다시 간다
기각한 것  검토했다가 안 하기로 한 것. "이렇게 하면 되지 않나"를 미리 막는다
```

⚠️ **WORK_LOG 커밋은 기능 커밋과 섞지 않는다.** 세션 끝에 하나씩, 별도로.
통합 머지는 **기능 커밋까지만** 가져간다(7/11에 딸려 들어간 사고 후 만든 규칙).

## 2026-08-06 · 회의 — 결손을 어디로 보낼 것인가 (+ 구현 4건)

제출까지 2주. **깊이보다 사이클**로 가되, 그 전에 "틀린 걸 다시 만날 자리가
단원 평가뿐"인 구멍을 메우기로 했다. 아래는 대화에서 뒤집힌 것들이라
결론만 보면 왜 그렇게 됐는지 알 수 없다.

### 기각한 것 — "다시 배우기" 화면

처음엔 내가(claude) **틀린 개념을 위한 별도 화면**을 제안했다. yoonhs가 별로라고
했고, 그게 맞았다. 이유는 두 개다.

- **우리가 이미 기각한 것과 같은 모양이다.** 파싱팀 `origin: inserted`(단원 삽입)를
  거절한 이유가 "목차는 고정, 결손은 다음 설명에 녹인다"였다. 이름만 바꾼 같은 것
- **설명을 다시 읽히는 건 인출이 아니다.** 인출 에이전트가 L1(정의문 베끼기)을
  강등시키는 이유가 그건데, 틀린 사람에게 같은 글을 다시 읽히면
  **"봤다"는 익숙함만 늘고 자기 상태를 더 잘못 읽게 된다**

yoonhs 정리: 결손은 이미 세 갈래로 흐른다 — 인출·형성에서 다시 나오고,
다음 단원 설명에 엮이고, **설명의 비중이 바뀐다.** 앞의 둘은 돌고 있었다.

### 뒤집은 것 — 늘리는 것과 줄이는 것은 대칭이 아니다

내가 "비중을 **줄이는 쪽**을 주력으로 하자(잘하면 스치고 지나가기)"고 했다.
yoonhs가 **"앞엣거 맞았다고 뒤엣거를 줄이는 게 더 이상한 로직"**이라고 했고,
이게 맞다.

```
앞 개념을 틀렸다  →  못 한다는 **증거가 있다**. 다음 개념의 선수면 얹는 게 근거 있는 행동
앞 개념을 맞혔다  →  다음 개념에 대해서는 **아무 증거도 없다**(아직 안 배웠다)
```

측정이 0인데 판정하는 것 — `MIN_WEIGHT`·`judged`로 계속 막아온 바로 그것을
내가 제안했다. **줄이는 건 그 개념 자체에 증거가 있을 때만**(진단에서 안다고
나왔거나 복습 이력이 있거나). 앞 개념 성적으로는 안 줄인다.

덧붙여 "같은 설명을 더 길게"라는 내 반론도 논점을 빗나갔다. yoonhs가 말한 건
길이가 아니라 **선수 개념 내용이 얹히는 것**이었다. 분량은 결과지 목표가 아니다.

### 정한 것 — 단원은 안 만들고, 화면은 만든다

yoonhs: *"목차 안에 페이지가 생기는 건 좋은데, 소프트웨어 구축 같은 목차가
새로 생기면 안 될 것 같다."*

```
단원 삽입  ✗  목차 목록이 바뀐다 — 파싱팀 origin:inserted 를 거절한 자리
화면 삽입  ✓  1단원이 1.29 → 1.30. 목차는 그대로다
```

이걸로 강약 두 단계가 규칙 하나로 설명된다.

```
가벼운 결손 (1~2회)          설명 안 ⚡ tie_in 한 줄 + 접힌 다시 설명
무거운 결손 (3회+ 선수관계)   그 화면 앞에 보충 화면
```

⚠️ 내가 "절 엔진 폐기 때문에 화면 수도 못 늘린다"고 했던 건 **오해였다.**
그때 버린 건 "개념을 우리가 묶어 절을 만들지 말자"지 "화면을 하나도 더 못
만든다"가 아니다. 삽입 화면의 개념도 이미 문서 안에 있다.

### 복습 시점은 새로 정할 게 없었다

yoonhs: *"하루 만에 틀린 걸 다시 내는 건 말이 안 되는 것 같은데."* — 맞힌 것에
대해선 정확하다. 우리 곡선을 재보니 이미 그렇게 되어 있다.

```
연속정답  0     1     2     3      4      5
복습 시점 2.2일 4.0  7.2  12.9  23.2  41.8      (표준 확장 간격과 거의 같다)
한 번 맞힌 뒤 남는 기억:  하루 79% · 이틀 63% · 사흘 50% · 일주일 20%
```

하루 뒤엔 79%가 남아 있어 다시 낼 이유가 없다. **틀린 것은 반대**지만, 그건
복습이 아니라 위의 보충 화면·tie_in이 맡는다(`needs_review`가 `last_success`를
요구하는 게 그 뜻이다).

### integration의 복습은 껍데기였다

```tsx
<ReviewGateModal items={reviewDue} onStart={moveToNext} onLater={moveToNext} />
```
"복습 퀴즈 시작하기"와 "다음에 할게요"가 **같은 함수**다. 복습 퀴즈가 없다.
배울 것은 **"넘어가려는 순간에 잡는" 타이밍**이고, 피할 것은 **전면 모달**이다
(학습을 잠갔다 이탈을 겪은 팀인데 여기서도 같은 실수를 했고, 선택까지 가짜였다).

## 2026-08-05 · 인출 라벨 검증

### 정한 것
- ★ **오측정이 미측정보다 나쁘다.** 게이트가 `concept` 라벨 개수만 잠그면
  "라벨 ≠ 실제 묻는 것"이 통과한다 → 숙련도가 거짓 신호를 먹는다
- 검증은 순수 로직(`retrieval_label.py`). 모델 kind 신고는 보조, 정답↔개념 매칭이 본체
- **이름 인출**(답이 라벨 개념)만 누락 게이트·숙련도 키에 넣는다
- **성질**(답이 개념명 아님)은 문항은 살리되 `concept_keys=()` — 화면이 숙련도에 안 붙임
- 정답이 **같은 화면 다른 개념** 또는 **문서의 다른 화면 개념**(`foreign_keys`)이면 폐기
- "정의/상황"이라 신고했는데 답이 개념명이 아니면 폐기(이름 인출 위장)
- 보충 프롬프트는 **상황·정의만** — 성질로 누락을 메우지 않는다

### 뒤집은 것
- ❌ **"게이트로 인출이 해결됐다"** → 개수만. 라벨 검증 전까지 오측정 구멍이 열려 있었다

### 된 것
- `retrieval_label.py` + `scrub_blocks`를 생성·보충 직후에 연결
- `retrieval_gap` = 이름 인출 기준
- `build_lesson`/`router`가 문서 타 화면 개념을 `foreign_keys`로 넘김
- 테스트 `test_retrieval_label.py` · 기존 gap 테스트 수정

### 검증에서 나온 것 (같은 세션, 다른 눈)

먼저 **잰 뒤에 판단했다.** 단위 테스트는 규칙이 의도대로 도는지만 잠근다 —
의도 자체가 틀렸는지는 실측이라야 나온다. 결함 둘 다 여기서 나왔다.

- ★ **같은 함수를 상대 크기가 다른 자리에 쓰면 안 된다.**
  `_answer_concept`에는 "표기가 조금 달라도 서로 **포함**이면 같게 본다"는 완화가
  있다. 상대가 이 화면 개념 두셋일 때는 맞다. 그대로 `foreign_keys`에 썼는데
  거긴 **문서 전체가 상대**다(실측 371개, 3자 이하가 59개).
  ```
  성질 정답 '이미 오름차순으로 정렬된 상태를 유지하는 배열의 일부'
      → 문서 어딘가의 개념 '상태'를 품었다는 이유로 폐기 (실제 생성물)
  정의문 377개를 정답이라 치고 재니 남의 개념으로 오인 117개 = 31%
      '모듈' ⊂ '모듈화'  ·  'WAS' ⊂ 'OWASP'  ·  '노드' ⊂ '단말 노드' (26쌍)
  ```
  ⇒ `_foreign_hit`으로 갈라 **정확 일치만** 본다. 잡아야 할 사고
  (`answer='XP(eXtreme Programming)'`)가 원래 그 모양이라 잃는 게 없다.
  **오폭 31% → 0%, 잡아야 할 것은 그대로 잡힘.**
- ★ **채점 귀속용 키와 측정용 라벨을 같은 칸에 두면 하나를 끌 때 둘 다 꺼진다.**
  성질 문항의 `concept_keys`를 비웠더니 `_levels_of`가 정의문을 못 찾고,
  `assess_cloze`가 "잴 수 없으면 강등 안 한다"로 L2를 준다. 결과적으로
  **정의문을 통째로 베낀 성질 문항이 L1 게이트를 그냥 통과한다.**
  ```
  scrub 전 [1]  →  scrub 후 [2]      (고치기 전, LLM 없이 재현됨)
  ```
  ⇒ 라벨을 `content.concept`에 남기고 `concept_keys`만 비운다. 객관식이 이미
  쓰던 방식이다. **워크로그에 이미 있던 원칙의 재발** — *원문 밖 정보는 필드를
  나눠라*(비유·tie_in). 같은 벽을 칸 이름만 바꿔 또 만났다
- 오폭은 **조용하다.** 문항이 하나 없어져도 화면은 멀쩡해 보이고 커버리지에도
  안 잡힌다(성질은 원래 안 세니까). 폐기에는 **사유별 카운트**가 있어야 한다 —
  이번엔 `scrub_blocks`를 감싸 밖에서 셌다(`bench/scrub_probe.py`)

- **14화면 전부 보충이 돌았다.** 1차 생성만으로는 이름 인출이 늘 모자라니

  `tiedIn=['디자인 패턴']`, 본문도 재생성됨
- ★ **네 출처가 하나로 누적된다**(`mastery.py` 재작성). 진단·인출·복습·형성이
  전부 `Attempt(kind, ...)`로 들어와 하나의 준비도가 된다
  ```
  준비도 = 이해도 × 진도 × 회상 강도
  ```
- **회상 강도**(망각곡선) — 마지막 성공 이후 감쇠. 반감기 3일에서 시작해
  연속 성공마다 늘어난다(3연속이면 17.5일). 🔁 복습 배지가 여기서 나온다

### 정한 것
- **약점은 절 단위로 짚는다.** 목차 단위로만 넘기면 목차 하나가 절 20개라 반영이
  20절 뒤에 나타난다. 학습자는 체감을 못 한다
- **이어지는 것만 녹인다.** 선수관계이거나 분류어를 공유할 때만
  (`자료 결합도`↔`제어 결합도`는 `결합도`를 공유). 실측(필기) 직전 절 개념을
  틀렸을 때 12/99에서만 판정 — **낮은 게 맞다.** 억지로 엮으면 설명이 산만해진다
- **출처마다 가중이 다르다** — 진단 0.5 · 인출 1.0 · 복습 1.5 · 형성 2.0.
  진단 오답은 **아직 안 배운 것**이지 무지의 증거가 아니다. 1.0을 주면 초반 오답이
  영원히 발목을 잡는다(`improving`을 만들 때 겪은 것과 같은 문제).
  복습 정답은 시간이 지나고도 꺼낸 것이라 훨씬 센 증거다
- **망각은 이해도를 안 깎는다.** 가만히 있는데 숫자가 내려가면 화면에서 설명할 수
  없다. `이해도`(안 떨어짐)와 `회상`(떨어짐)을 따로 두고 준비도에서 곱한다.
  `understanding`을 따로 내보내는 이유: 준비도가 낮은 게 **잊은 것**인지
  **아직 모르는 것**인지 갈라야 처방(복습 vs 다시 학습)이 나온다
- 판정 자격도 가중으로 (`MIN_ATTEMPTS 3회` → `MIN_WEIGHT 3.0`)

### 뒤집은 것
- **"약점 문단을 설명 본문 안에 넣어라"는 안 먹힌다.** 처음엔 프롬프트에
  `🔍 여기서 잠깐 —`으로 시작하는 문단을 본문에 넣으라고 했다. 관련 있는 절에서도
  **0회**였다(본문 318자로 짧게 쓰며 밀어냄). **비유를 별도 필드로 뺐을 때와
  같은 문제** — 학습자 이력에서 온 정보라 "원문 사실만 써라"와 프롬프트 안에서
  충돌하고, 모델은 안전한 쪽(안 씀)을 택한다. `tie_in` 별도 필드로 빼니 나온다.
  ⇒ **원문 밖 정보는 전부 필드를 나눠라.** 이걸로 두 번째다
- **"한 번도 못 맞힌 절도 복습 대상"** — 형성평가 오답 1건뿐인 절이 "복습 대기"로
  잡혔다(실측에서 발견). 그건 아직 모르는 것이라 처방이 다르다. 복습은 **맞힌 적
  있는데 잊혀가는 것**이다. `needs_review`에 `last_success` 조건을 걸었다
- **"DB가 없어서 누적이 안 된다"** — 윤현석 추정이었고 틀렸다. 인메모리에서도
  누적은 됐다(4문제 후 약점 개념 추출 확인). 원인은 배선 부재였다
- ★ **"인출 밀도를 개념 단위로 바꿔서 해결됐다"** — 아니었다(리뷰에서 잡힘).
  **단위만 바뀌고 강제가 없었다.** "빈칸은 개념마다 하나씩"이 프롬프트의 부탁으로만
  남아 있었고, 재시도 루프는 `l1_ratio`만 보고 `gap`은 계산해서 화면에 내보내기만
  했다. 14절 실측에서 재시도가 **한 번도 안 걸렸다**
  ```
                      전      후
    인출된 개념      39/48   47/48   81% → 98%
    빠짐 없는 절      6/14   13/14   43% → 93%
    개념당 빈칸       0.83    1.00
  ```
  → **품질과 누락은 처방이 다르다.** L1이 높으면 만드는 방식이 잘못된 것이라 전체를
  다시 만들어야 하고, 누락은 나머지가 멀쩡하므로 **그 개념만 다시 요청해 덧붙인다.**
  누락을 전체 재생성으로 고치면 잘 나온 문항까지 흔들린다(같은 절이 생성마다
  빈칸 1개↔5개로 출렁였다). 덧붙이기는 결과가 단조 증가한다
  → **범위를 좁혀 시켜야 한다.** 개념 10개 중 2개가 빠졌을 때 10개를 다시 시키면
  또 8개만 만든다. 2개만 시키면 2개를 만든다(`•4회전` 절: 빈칸 2 → 보충 8 → 10/10)
- ★ **"게이트로 인출이 해결됐다"** — **개수만** 해결됐다. 게이트가 `concept` **라벨**로
  세기 때문에 "라벨 ≠ 실제 묻는 것"이 그대로 통과한다. `0-8cdd5ac9` 4문항 중 2개:
  ```
  concept='애자일 모형'     answer='XP(eXtreme Programming)'  ← 다른 절 개념이 정답
  concept='프로토타입 모형'  answer='견본·시제품'              ← 성질 유형(의도)
  ```
  성질 유형은 프롬프트가 허용한 설계다(`※ 성질 유형의 answer는 예외`). 문제는
  **숙련도가 그걸 구분 없이 라벨 개념에 기록**한다는 것 — 성질 문항을 맞혀도
  "그 개념을 꺼낼 수 있다"의 증거는 약하다. ⇒ **미측정이 오측정으로 바뀔 수 있다.**
  정답이 **이 절 밖 개념**인 건 유형과 무관하게 그냥 사고다(XP 케이스)
  → 개념마다 상황·정의 유형 **최소 1개는 보장**하고 성질은 그 위에 추가.
    정답이 절 밖 개념이면 폐기. `retrieval_level`이 이미 유형을 판정하므로 재료는 있다

### 정한 것
- **용어는 파싱 md를 그대로 따른다** — `문서·목차·조각·개념`. 새로 만든 말은 `절` 하나뿐.

- **화면 계층은 자료 → 목차 → 절 3장.** 한 응답에 다 말아 넣지 않는다.
  조각(chunk)은 API 밖으로 안 나간다 — 4,000자 호출 예산이라 사용자에게 의미가 없고
  파싱이 바뀌면 제일 먼저 바뀔 부분이다
- **절 묶기는 공통층**(문서당 1회·캐시), 숙련도만 개인층. 개인층에 두면 ③에 LLM이

- **진단은 목차를 안 바꾸고 분량을 바꾼다.** 목차는 교재 것이고 곧 시험 범위다.

- **절 순서 = 원문 등장 순서.** "묶은 순서"는 규칙 적용 순서라 순서가 아니다.
  PDF에서 찾는 문제는 순서가 아니라 쪽 표시로 푼다
- **인출 밀도는 B**(개념당 빈칸 1 + 절당 객관식 1, 총 ~470개). 총량이 문제되면

- **md는 서버 시작 시 fixture로 프리로드.** 업로드 흐름은 파싱 팀과 통합할 때 다시 짠다
