# 문제 검증 흐름도 — 만들어진 문제가 합격 판정을 받기까지

> 문제가 만들어지기까지의 과정은 **[문제 생성 흐름도](QUIZ_FLOW_GENERATION.md)** 참고.
> 예시는 생성 흐름도에서 만들어진 문제로 이어집니다: **"GROUP BY로 그룹화된 결과에 조건을 지정하는 절은 무엇인가?" (정답: HAVING, 근거: 교재 13쪽 문장)**

## 왜 이렇게까지 검증하나

AI가 만든 문제는 그럴듯해 보여도 **정답이 틀렸거나, 정답이 두 개거나, 원문에 없는 얘기**일 수 있습니다. 실측이 그랬습니다: 검증을 갖추기 전 첫 실험에서는 **저장된 문제 4개 중 쓸 만한 것이 1개(25%)** 였고, 검사를 보강해 가며 8회차에는 이 비율이 **74%** 까지 올랐습니다 (회차별 기록: QUIZ_TUNING.md).

그래서 만든 AI 말고 **다른 AI들이 검토하고, 심지어 직접 풀어보게** 합니다. 생성된 문제의 절반 안팎이 여기서 떨어집니다 (실측 예: 12회차 저장 11·폐기 29, 19회차 저장 21·폐기 21). 두 가지 주의:

- 폐기분이 전부 나쁜 문제라는 뜻은 아닙니다 — 검증기의 오판도 섞여 있습니다 (맨 아래 "검증기 자체도 검증한다"에서 측정).
- 반대로 **폐기율이 낮다고 품질이 좋은 것도 아닙니다** — 실측에서 폐기율 0%였던 회차의 저장분 6개 중 4개가 결함이었습니다 (검증기가 아무것도 못 걸렀다는 뜻). 그래서 품질 지표는 폐기율이 아니라 **"저장분 중 실사용 가능 비율"**을 씁니다.

## 검증단 구성 — "서로 다른 두 검토자"


| 역할    | 담당                      |
| ----- | ----------------------- |
| 검토자 1 | 솔라 (문제를 만든 것과 같은 회사 모델) |
| 검토자 2 | 엑사원 (다른 회사 모델)  |


**왜 이 구성인가** — 전부 교차 실험(10회차 전후, QUIZ_TUNING.md §10)으로 정한 것입니다:

- **만든 것과 같은 회사 모델이 1차 검토를 하는 게 이상해 보이지만**, 검수자 역할 지시문을 주면 자기 회사 모델이 만든 문제의 결함도 대부분 잡습니다. 문제는 같은 혈통이 공유하는 맹점 — 그래서 **다른 회사 모델을 2차로** 붙입니다. 실측에서 엑사원이 단독으로 잡은 결함이 16건: "정답이 원문에 없고 추론으로 생성됨", "'강제 접근통제'/'강제 접근 통제' 표기 차이(완전일치 채점에 치명)" 등 전부 솔라가 통과시킨 것들입니다.
- **엑사원으로 교체하지 않고 추가만 한 이유**: 엑사원을 단독 검토자로 세운 교차 실험에서는 응답 형식이 자주 깨져 멀쩡한 문항까지 대량 탈락했습니다. 그래서 솔라 판정을 그대로 두고 2차로만 씁니다 — 최악의 경우에도 솔라 단독보다 나빠지지 않는 구성.
- **어느 한쪽이라도 "불합격" 판정을 내리면 탈락**합니다. 합의제가 아닌 이유: 위 16건처럼 한쪽만 잡는 결함이 실제로 있기 때문입니다. 이 규칙은 멀쩡한 문제를 떨어뜨리는 방향의 위험을 키우므로 반대쪽 안전장치와 세트입니다 — 검토자 2가 알아볼 수 없는 답변을 하거나 이유 없이 불합격만 표시하면 **그 판정은 무시**(기권 처리)합니다.
- 엄격함의 비용도 측정돼 있습니다: 배심원단 도입 회차에서 저장 22문항 vs 도입 전 32문항. 덜 저장되는 대신 나쁜 문제가 은행에 들어가지 않는 쪽을 택했고, 모자라는 양은 생성 단계의 과생성(예산 ×1.15)으로 보충합니다.
- 순서는 비용이 안 드는 검사부터: 코드 점검 → AI 검토 → AI가 직접 풀어보기.



## 전체 흐름 한눈에 보기

```
만들어진 문제들
   │
   ▼
1단계  기계 점검 (코드가 자동으로) — 형식·금지 패턴 걸러내기
   │  통과한 것만
   ▼
2단계  검토자 1(솔라)의 검토 ★ 8가지 체크리스트
   ▼
3단계  검토자 2(엑사원)의 검토 — 같은 체크리스트, 다른 시각
   │  살아남은 것만
   ▼
4단계  검토자 1이 직접 풀어보기 ★ 정답 가리고, 원문만 주고
   ▼
5단계  검토자 2도 직접 풀어보기
   │
   ▼
6단계  탈락한 문제는 한 번 수정 → 1~5단계 재검사
   │
   ▼
7단계  최종 — 합격만 저장, 탈락은 이유 기록
```

## 1단계. 기계 점검 (코드가 자동으로 — 비용 0)

AI에게 물어볼 필요도 없이 기계적으로 판별 가능한 것들을 먼저 거릅니다:


| 확인하는 것                                   | 왜                                                      |
| ---------------------------------------- | ------------------------------------------------------ |
| 객관식 선지가 정확히 4개인가, 중복 선지는 없는가             | 형식 계약                                                  |
| 객관식 오답 고르기 (아래 상세)                    | 문제를 만들 때 오답 후보를 일부러 넉넉히(6~7개) 만들게 하고, 코드가 중복·정답과 같은 표기를 걸러낸 뒤 **정답과 길이가 비슷한 순으로 3개** 선별 |
| 빈칸 정답이 너무 길지 않은가 (15자 초과 = 구절을 통째로 비운 것) | 구절을 통째로 비우면 사람이 완전일치로 똑같이 못 씀 → 채점 불가. 15자는 실측 사고 표본(구절 통째 빈칸)을 기준으로 정한 경험적 컷 |
| **빈칸이 "=" 바로 뒤에 있지 않은가**                 | "64−2=(빈칸)"은 문제 자체가 답을 계산으로 알려주는 꼴                     |
| 빈칸 정답이 지문에 그대로 남아 있지 않은가                 | 답이 보이는 문제 방지                                           |
| 문제에 "~입니다", "~해요" 같은 존댓말·구어체가 없는가        | 시험 문체 위반 (아래 상세)                                    |
| 문제에 내부 문장 번호(s38 등)가 노출되지 않았는가           | 시스템 내부 표기 유출 방지                                        |

**오답 선별의 기준이 왜 "길이"인가** — 코드는 오답이 내용적으로 그럴듯한지 판단할 수 없습니다. 코드가 판단할 수 있는 것만 맡습니다:

- **거르기(확실한 판단)**: 표기 정규화 후 문자열 비교로 중복 후보와 정답과 같은 후보를 제거
- **고르기(대리 지표)**: 정답과 **글자 수가 비슷한** 순으로 3개 — 선지 하나만 유난히 길거나 짧으면 그게 정답이라는 단서가 되기 때문(수험 요령으로 알려진 현상). 후보를 넉넉히 만들게 한 뒤 걸러 뽑는 이 방식은 오답 생성 연구(overgenerate-and-rank)의 경량판입니다
- **못 하는 것**: "이 오답이 사실상 맞는 말 아닌가"는 코드로 판단 불가 — 그래서 오답 후보마다 생성 AI에게 "왜 오답인지"를 쓰게 하고, 선별이 잘못됐으면 2~3단계 검토(오답이 원문에서 참이면 불합격)와 4~5단계 풀이(풀이자가 복수 정답 판단)가 걸러냅니다

**존댓말이 왜 불합격 사유인가** — 이유는 세 겹입니다:

1. **만드는 게 모의 시험지라서.** 실제 시험 발문은 전부 "~은 무엇인가?", "~이다" 문어체 평서형입니다. "~인가요?", "~입니다"가 섞이면 문항마다 말투가 들쭉날쭉해져 시험지로서의 완성도가 무너집니다.
2. **존댓말은 AI가 출제자 역할에서 이탈했다는 신호라서.** 경어체가 나왔다는 건 모델이 챗봇 말투로 미끄러졌다는 뜻이고, 이때는 인사말·학습 조언 같은 시험 범위 밖 오염이 같이 딸려오는 경향이 있습니다.
3. **AI 검토자가 이걸 잘 놓쳐서.** "예측합니다" 같은 문체 위반을 검토자 둘 다 통과시킨 실측 사고가 있어, 비용 0인 기계 검사(어미 패턴 대조)로 내려왔습니다. 단 "아니다"처럼 시험 문체에 흔한 말도 '니다'로 끝나는 함정이 있어, "~습니다/~ㅂ니다" 꼴만 정확히 걸러냅니다.

그리고 여기서 걸려도 바로 폐기 확정은 아닙니다 — **6단계 수정 루프에서 문체만 고치면 살아날 수 있는**, 탈락 사유 중 가장 회생하기 쉬운 축입니다.

**예시**:

```
✅ "그룹화된 결과에 조건을 지정하는 절은 무엇인가?" (단답형, 정답 HAVING)
   → 질문·정답·해설 전부 있음, 존댓말 없음, 문장 번호 노출 없음 → 통과

❌ 빈칸 문제 "64 − 2 = [____]"                → "=" 뒤 빈칸 (답이 계산으로 노출) → 폐기
❌ 객관식인데 선지가 3개                        → 폐기
❌ "s12에 따르면 옳은 것은 무엇입니까?"          → 내부 번호 노출 + 존댓말 → 불합격 (6단계 수정 대상)
```

## 2~3단계. AI 검토자의 검토

문제를 몇 개씩 묶어 검토자에게 보냅니다. 검토자에게 주는 지시문(요약):

> **너는 출제 검수자다. 각 문제를 근거 원문과 대조해 판정하라.**
>
> 채점은 사람이 아니라 코드가 한다. 유형별로 채점 방식이 다르니 **잣대를 헷갈리지 마라**:
>
> - 객관식은 선지 **번호**로, OX는 **참/거짓**으로 채점된다 — 정답 문구가 원문과 똑같은 표현인지는 상관없다
> - 단답형·빈칸만 글자 대조로 채점된다 (그마저 띄어쓰기·대소문자는 무시하고, 인정 표기 목록도 있다)
>
> **하나라도 어기면 불합격:**
>
> 1. 정답이 근거 원문으로 뒷받침되는가? (토씨까지 같아야 한다는 뜻이 아니다 — 뜻으로 도출되면 합격)
> 2. 정답이 유일한가? 문제 설명에 들어맞는 답이 원문에 둘 이상이면 불합격. (객관식) 오답 선지가 원문 기준으로 사실상 맞는 말이어도 불합격 — 정답이 2개가 되는 문제
> 3. (단답·빈칸) 정답을 그대로 받아쓸 수 있는가? 답이 문장이거나 표현이 여러 가지면 불합격
> 4. (빈칸) 빈칸이 2개일 때, 두 답을 서로 바꿔 넣어도 말이 되면 불합격 (채점이 빈칸 순서를 따지므로 정답이 유일하지 않게 됨)
> 5. 발문·해설·선지 전부 시험 문체인가? 구어체·존댓말이면 불합격
> 6. 내부 문장 번호가 노출되지 않았는가?
> 7. (빈칸) 빈칸이 번호·기호처럼 의미 없는 자리가 아닌가?
> 8. 표현에 모순·모호함이 없는가? 이 사유로 불합격시킬 때는 어느 표현이 어떻게 모호한지 구체적으로 적을 것
>
> **다음은 불합격 사유가 아니다** (검토자들이 실제로 자주 하는 오판):
>
> - 객관식·OX에서 정답 "문구"가 원문 표현과 다른 것 — 번호/참거짓으로 채점되므로 무관
> - 정답 단어가 원문에 토씨 그대로 없는 것 — 뜻으로 뒷받침되면 합격

체크리스트에 **일부러 안 넣은 것**도 있습니다 — 코드가 이미 결정적으로 보장하는 항목을 AI에게 다시 물으면, 잘못 판정해서 멀쩡한 문제를 떨어뜨릴 위험만 남기 때문입니다:

| 안 묻는 것 | 코드가 보장하는 방식 |
|---|---|
| 선지가 4개인가 | 1단계에서 코드가 오답 후보 중 3개를 골라 4개로 조립하고, 4개가 아니면 그 자리에서 폐기 |
| 빈칸이 3개 이상인가 | 1단계 기계 점검이 2개 초과를 폐기 |
| 빈칸 채운 문장이 자연스러운가 | 빈칸 지문은 근거 문장 그대로 조립되므로, 채우면 항상 원문 문장과 동일 |

검토자 2(엑사원)에게는 한 가지를 다르게 줍니다: 지시문 속 **예시 문구를 전부 빈칸 처리** — 예시를 그대로 베껴서 판정 이유로 내는 버릇이 실측으로 확인됐기 때문입니다.

**예시** — 검토자가 돌려주는 판정:

```
문제: "그룹화된 결과에 조건을 지정하는 절은 무엇인가?" (정답 HAVING)
근거: "HAVING 절은 GROUP BY로 그룹화된 결과에 조건을 지정한다."

검토자 1: { 합격 }                          → 정답이 근거 문장으로 뒷받침됨
검토자 2: { 합격 }                          → 통과, 다음 단계로

(탈락 예) 객관식 "단위 테스트의 특징은?"에서
검토자: { 불합격, 이유: "오답 선지 중 하나가 원문 기준으로 사실상 맞는 말 — 정답이 2개가 됨" }
→ 이 문제는 여기서 탈락, 6단계(수정)로
```

## 4~5단계. AI가 직접 풀어보기

"정답이 하나뿐인가?"를 **말로 묻지 않고 실험**합니다: 정답과 해설을 전부 가린 문제를, 근거 원문과 함께 주고 실제로 풀게 합니다.

원문을 함께 주는 이유 — 확인하려는 것이 "풀이 AI가 이 지식을 아는가"가 아니라 **"이 문제가 근거 문장만으로 풀리는가"**이기 때문입니다. 원문 없이 풀게 하면 풀이 AI의 배경지식 시험이 되어버려서, 문제 자체의 결함(근거로 안 풀림, 정답 둘)과 모델이 몰라서 틀린 것을 구분할 수 없게 됩니다.

> **너는 수험생이다. 각 문제를 근거 원문만 보고 풀어라.**
>
> - 객관식: 정답이라고 볼 수 있는 선지 번호를 **전부** 적어라 — 둘 이상이면 둘 다 적어라 (억지로 하나만 고르지 마라)
> - 빈칸: 빈칸 순서대로 답을 적어라 / 단답형: 답 하나 / OX: 참 또는 거짓

풀이 결과 판정:


| 풀이자가…         | 판정                                |
| ------------- | --------------------------------- |
| 정답을 맞힘        | 통과                                |
| 다른 답을 고름      | 탈락 — 문제가 모호하거나 근거로 풀 수 없다는 실험적 증거 |
| "정답이 2개 같은데요" | 탈락 — 정답 유일성 붕괴                    |


채점은 **실제 서비스와 똑같은 채점 코드**를 씁니다 (그래야 검증 결과가 실제 사용 환경과 일치합니다). 풀이 AI의 사소한 표기 차이(답을 따옴표로 감싸거나, 선지 번호 대신 선지 내용으로 답하는 것)는 내용이 맞으면 정답으로 인정합니다 — 확인하려는 건 "이 문제가 풀리는가"이지, 풀이 AI의 표기 방식이 아니기 때문입니다.

**예시**:

```
문제(정답 가림): "GROUP BY로 그룹화된 결과에 조건을 지정하는 절은 무엇인가?"
근거 원문 함께 제공: "HAVING 절은 GROUP BY로 그룹화된 결과에 조건을 지정한다."

풀이 AI 1의 답: "HAVING"        → 정답과 일치 → 통과
풀이 AI 2의 답: "HAVING 절"     → 인정 표기 목록에 있음 → 통과

(탈락 예) "물리적 자원을 가상화하는 클라우드 서비스는?" (출제 정답: IaaS)
풀이 AI의 답: "DaaS"  → 근거 원문만으로는 IaaS와 DaaS가 구분이 안 된다는 실험적 증거 → 탈락
```

여기도 검토자 2에게는 예시 답을 빈칸 처리해서 줍니다 (예시 답 "[2]"를 진짜 답인 양 베끼는 버릇 실측).

## 6단계. 탈락한 문제는 한 번 수정해서 다시 검사

탈락한 문제는 **탈락 이유를 첨부해서** 문제를 만든 AI에게 돌려보내 수정시킵니다:

> 아래 문제들이 검수에서 불합격했다. **불합격 사유를 해소하도록** 고쳐라.
>
> - 사유를 해소하는 최소한의 수정만. 개념과 유형은 바꾸지 마라
> - 원문에 없는 사실 금지
> - **고칠 수 없으면 그 문제는 포기해라 — 억지 수정 금지**

수정된 문제는 1~5단계를 **처음부터 다시** 통과해야 합니다. 수정 기회는 한 번뿐입니다 — 이건 실측으로 정한 값이 아니라 비용 쪽 설계 결정입니다: 수정 한 바퀴마다 검증 전체(AI 검토·풀이 호출 포함)가 한 바퀴 더 돌아서, 1회로 제한했습니다. 2회 이상 수정의 추가 효과는 측정된 적이 없습니다.

탈락 사유마다 회생 확률이 다릅니다: **존댓말 같은 문체 위반은 표현만 바꾸면 되므로 가장 살아나기 쉽고**, 반대로 "정답이 원문에 없음"은 원문에 없는 사실을 못 쓰게 돼 있어서 사실상 회생이 어렵습니다(그래서 포기 지시가 있는 것).

예외: 빈칸 문제는 수정 대상에서 제외합니다 — 빈칸 지문은 코드가 조립하는 것이라, AI가 고치는 과정에서 정답이 지문에 다시 노출되는 사고가 실제로 있었기 때문입니다.

**예시**:

```
탈락 문제: 객관식 "단위 테스트의 특징은?"
탈락 이유: "오답 선지 ③이 원문 기준으로 사실상 맞는 말 — 정답이 2개"

수정 결과: 선지 ③을 원문에 없는 다른 오답으로 교체
재검사:   1~5단계 다시 통과 → 합격 (수정으로 살아난 문제로 표시)

수정 불가면: AI가 그 문제를 출력에서 뺌 → 원래 탈락 판정 유지
```

| --- | --------------------------------------- |

| 탈락  | 저장 안 함. "어느 단계에서, 왜 떨어졌는지"만 기록 (품질 분석용) |


## 검증기 자체도 검증한다

검토자·풀이자도 AI라서 판정이 틀립니다. 검증기 쪽 결함을 찾고 고치는 수단으로 현재 있는 것은 두 가지입니다.

**① 재검증 도구** (`backend/scripts/reverify_quiz.py`) — 저장된 문항을 데이터베이스에서 읽어 같은 검증(1단계 기계 점검 + 검토 + 풀이)에 다시 넣고 통과율을 측정합니다. 데이터베이스는 읽기만 하고(삭제·수정 없음), 6단계 수정 루프는 끕니다 — 목적이 문제를 고치는 게 아니라 "저장분 중 실사용 가능 비율" 측정이기 때문입니다.

한 번 합격해서 저장된 문항들을 다시 넣었는데 대량으로 떨어지면, 그 차이는 문항 결함이 아니라 검증기 오판이라는 신호입니다. 실측 기록 (같은 151문항 반복 측정, 08-08):

```
32% (49/151)  최초 측정. 탈락 사유를 보니 문항 결함이 아닌 것이 다수:
              풀이자의 배치 응답 JSON이 깨져 답이 옆 문항과 뒤바뀜,
              OX 답을 'False' 문자열로 써서 채점 불일치 등
 → 49%       응답 처리 수정: 답을 문항 번호(index) 기준으로만 매칭(위치 추측 금지),
              판독 불가 응답은 같은 묶음으로 1회 재질의,
              검토자 2의 사유 없는 불합격은 기권 처리
 → 51%       검토 지시문 수정: 유형별 채점 방식 명시("객관식은 번호로 채점")
              + "다음은 불합격 사유가 아니다" 목록 추가
 → 59%       풀이 지시문의 예시 답 빈칸 처리
              (검토자 2가 예시 값 "[2]"를 실제 답으로 복사하는 것 확인)
```

같은 문항인데 통과율이 32%→59%로 올랐다 = 그 27%p만큼이 검증기 쪽 결함이었다는 뜻입니다. 여기서 나온 수정은 전부 검증기 코드에 반영돼 이후 생성 검증에도 그대로 적용됩니다.

**② 회차별 저장분 확인** — 생성 실험을 돌릴 때마다 저장된 문항을 확인해 실측 기록(QUIZ_TUNING.md)에 남깁니다. 기록 예: 10회차 저장 22문항 확인 — 문장 번호 유출 0건, 시험 문체 100%, 유형 분포 객관식 10/단답 8/OX 3. 여기서 발견된 결함은 코드 검사로 옮깁니다 — 11회차에서 "~예측합니다" 경어체 문항이 검토자 둘 다 통과한 것이 확인되어, 1단계 기계 점검에 경어체 어미 검사가 추가됐습니다.

**현재 검증기 코드에 들어 있는 안전장치** — 전부 위 측정에서 확인된 사고에 대응해 추가된 것입니다:

| 안전장치 | 대응한 사고 |
|---|---|
| 판독 불가 응답은 같은 묶음으로 1회 재질의 | 검토 AI의 응답 형식이 깨진 것을 문항 결함으로 처리해 폐기 |
| 답을 문항 번호(index)로만 매칭, 깨진 응답에서 위치로 추측하지 않음 | A문항의 답이 B문항에 붙어 멀쩡한 B가 탈락 |
| 재질의에도 판독 불가면: 검토자 1은 불합격 처리, 검토자 2는 기권(1차 판정 유지) | 검토자 2의 응답 형식 붕괴로 멀쩡한 문항이 대량 탈락 |
| 검토자 2의 사유 없는 불합격은 기권 처리 | 이유 없이 불합격만 표시하는 판정 |
| 검토자 2에게 주는 검토·풀이 지시문에서 예시 문구·예시 답을 빈칸 처리 | 예시 문구를 판정 사유로, 예시 답 "[2]"를 실제 답으로 복사 |
| 검토 지시문에 유형별 채점 방식과 "불합격 사유가 아니다" 목록 명시 | 단답형 잣대(글자 대조)를 객관식(번호 채점)에 적용해 오탈락 |
| 검토자 2의 판정 사유에 [배심] 태그 | (사고 대응이 아니라 추적용 — 탈락 사유가 어느 검토자에게서 나왔는지 기록) |
