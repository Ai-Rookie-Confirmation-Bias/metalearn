## 2. 새 API 2개

### 개념 검색 — `GET /api/parsing/concepts/search`

개념을 **뜻으로** 찾는다. 문서 경계를 넘는다.

| 파라미터 | 기본 | 설명 |
| --- | --- | --- |
| `q` | (필수) | 찾을 개념 이름이나 설명 |
| `limit` | 10 | 1~50 |
| `min_sim` | 0.0 | 이 유사도 미만은 버린다 |
| `document_id` | 전체 | 여러 번 주면 그 자료들 안에서만 |

```bash
curl "http://localhost:8000/api/parsing/concepts/search?q=cocomo&limit=5"
curl "http://localhost:8000/api/parsing/concepts/search?q=소프트웨어%20비용%20산정"
curl "http://localhost:8000/api/parsing/concepts/search?q=cocomo&document_id=<uuid>"
```

```json
[
  {
    "id": "…", "name": "COCOMO 모형",
    "definition": "보헴이 제안한 LOC 기반 소프트웨어 비용 산정 기법",
    "source": "book", "global_key": "cocomo-model",
    "similarity": 0.579,
    "document_id": "…", "filename": "pilgi.pdf",
    "topic_title": "5. 정보시스템 구축 관리",
    "evidence": [ { "segment_seq": 13, "sentence_seq": 18,
                    "char_start": 472, "char_end": 532,
                    "text": "보헴(Boehm)이 제안한 것으로, 원시 프로그램의 규모(LOC)에 의한 …",
                    "page_from": 34, "page_to": 37 } ]
  }
]
```

**이름이 안 겹쳐도 찾는 게 요점이다.** 실측: `소프트웨어 비용 산정`으로 검색하면
그 말이 이름에 없는 `Cost Estimation`(0.723) · `COCOMO 모형`이 올라온다.

주의 두 가지:

- **한글로 약어를 치면 약해진다.** `cocomo` 0.579 vs `코코모` 0.421. 영문 약어는
  영문으로 검색하는 편이 정확하다.
- 검색어는 내부에서 **query 모델**로 임베딩한다. 개념 벡터가 query 모델로
  만들어져 있어서다 — passage로 넣으면 실측에서 0.579 → 0.399로 떨어졌다.
  (조각 본문을 찾을 때는 반대로 passage다.)

### 근거 위치 — `GET /api/parsing/documents/{id}/tree`

기존 트리 응답의 개념에 `evidence`와 `global_key`가 추가됐다.

```json
{
  "id": "…", "name": "모듈",
  "definition": "모듈화를 통해 분리된 시스템 기능 단위로, 단독 컴파일 및 재사용이 가능함",
  "source": "book", "global_key": "module",
  "segment_seqs": [1],
  "prerequisite_ids": ["…"],
  "evidence": [
    { "segment_seq": 1, "sentence_seq": 88,
      "char_start": 2433, "char_end": 2462,
      "text": "- •모듈화를 통해 분리된 시스템의 각 기능들이다.",
      "page_from": 4, "page_to": 6 }
  ]
}
```

**좌표계는 조각 기준이다.** `char_start`/`char_end`는 그 조각 `content` 안의
offset이라 정확하다. 반면 페이지는 **조각의 범위**(`page_from`~`page_to`)이고
문장 하나의 정확한 페이지가 아니다 — 조각이 여러 페이지에 걸치기 때문이다
(실측: 조각 1 = p.4~6). 화면은 조각 본문을 통째로 받아 이 구간만 강조하면
원문 대조가 정확히 맞는다.

근거 부착률은 실측 99%(개념 397개 중 394개)다. 빈 배열은 두 경우다 —
LLM이 근거를 특정하지 못했거나, 원문에 없는 선수개념(끊긴 고리)이라 근거가
있을 수 없거나.

**근거 문장이 항상 정확하지는 않다.** 3개 중 1~2개는 개념을 정확히 짚고
나머지는 인접 문장을 함께 집는 수준이다. 위치를 짚어주는 용도로는 쓸 만하고,
"이 문장만 딱 보여준다"에는 검증이 한 겹 더 필요하다.

### 코스를 시작하기 전에 필요한 것 — `GET /api/courses/{id}/prereqs`

12.5가 뽑은 선수 후보를 **이 코스의 실제 자료들과 대조해** 거른 결과다.
첫 호출에서 계산·저장하고 이후는 조회뿐이다.

```bash
curl "http://localhost:8000/api/courses/{id}/prereqs"
curl "http://localhost:8000/api/courses/{id}/prereqs?status=pass,gray"  # 화면용
curl "http://localhost:8000/api/courses/{id}/prereqs?refresh=true"      # 자료 바꿨을 때
```

```json
[ { "subject": "리눅스 기초", "item": "SSH를 통한 원격 접속",
    "why": "EC2 인스턴스 운영 이해를 위해",
    "seq": 1, "ordered": false,
    "status": "pass", "similarity": 0.428, "rejected_by": "라우팅",
    "known": null } ]
```

`status`가 셋인 이유가 중요하다.

| | 뜻 | 화면 |
| --- | --- | --- |
| `pass` | 확실히 책 밖 | 그냥 보여준다 |
| `gray` | 자료에 조금 나온다 | 보여주되 "△ 자료에 조금 나옴" 표시 |
| `rejected` | 자료가 확실히 가르친다(유사도 0.75↑) | 숨긴다 |

**`gray`를 숨기지 않는 게 설계다.** LLM 판정이 실행마다 뒤집혀서
(`라우팅 원리`가 한 번은 통과, 한 번은 기각) 판정으로 항목을 지우게 두지
않았다. 항목 하나가 더 뜨는 건 훑으면 되지만, 안 뜬 항목은 물어볼 기회 자체가
사라진다. `rejected`는 임베딩 0.75 이상만 — `CIDR 표기법`(0.783)처럼
흔들리지 않는 것들이다.

`known`은 24번 진단이 채운다(`known|heard|unknown`). 지금은 항상 NULL이다.

### 뼈대 목차 + 본문 설명 — `GET /api/courses/{id}/tree`

18번의 산출물이자 이 서비스가 하려는 것의 본체다. **PPT 순서로 가되 설명은
교재에서** 온다.

```bash
curl "http://localhost:8000/api/courses/{id}/tree"
```

```json
{ "course_id": "…", "title": "정보처리기사",
  "skeleton_document_id": "…", "body_document_ids": ["…"],
  "linked_concepts": 120, "total_concepts": 452,
  "topics": [
    { "seq": 0, "title": "1. 소프트웨어 설계", "origin": "book", "plan": "normal",
      "concepts": [
        { "name": "도커", "definition": "…",
          "evidence": [ { "segment_seq": 2, "sentence_seq": 41,
                          "char_start": 1180, "char_end": 1237, "text": "…",
                          "page_from": 6, "page_to": 9 } ],
          "body": [ { "name": "Docker", "filename": "실기요약노트.pdf",
                      "similarity": 0.9841, "kind": "same", "verified_by": "embed",
                      "definition": "…",
                      "segments": [ { "seq": 14, "content": "…",
                                      "page_from": 51, "page_to": 53 } ] } ] } ] } ] }
```

- **목차는 `course_topics`다** — 사용자가 고친 복사본이지 원본이 아니다
- `evidence`는 **뼈대 자료** 안에서의 근거 위치
- `body`는 **다른 자료**가 그 개념을 설명하는 곳. 조각 본문이 통째로 온다
- `kind=related`면 상위·하위 개념이라 설명이 조금 넓거나 좁을 수 있다
- 연결은 **문서쌍 단위로 저장**된다. 실측: 첫 호출 3.9초 → 두 번째 0.31초.
  같은 두 책을 쓰는 다음 사람은 계산이 없다

### 19' — 코스가 학습 화면에 닿는 길

여기까지가 값을 만드는 쪽이고, 그 값이 **화면에 보이는** 자리는 학습 API다.
`GET /api/curriculum/documents`가 파싱 문서와 함께 코스도 준다(코스에 묶인
자료는 목록에서 뺀다 — 같은 내용이 두 권으로 뜨면 안 된다).

```bash
GET  /api/curriculum/documents                        # 자료 + 코스
GET  /api/curriculum/documents/{course_id}            # 코스를 책 한 권처럼 연다
POST /api/curriculum/documents/from-course/{id}       # ?refresh=true 목차 변경 반영
```

변환은 `curriculum/adapters/course_tree.py`가 한다. 코스 트리와 문서 트리의
모양이 같아서(`topics[].concepts[].evidence[]`) 겉껍데기만 맞춰 주면 자르기·화면
만들기는 기존 어댑터를 그대로 쓴다. **다른 건 목차의 출처 하나뿐이다** —
`doc_topics`(교재 목차)가 아니라 `course_topics`(그 사람의 목차).

**조각은 자르지 않는다.** 단원마다 뼈대 조각과 본문 조각을 통째로 싣는다.
화면으로 자르는 건 받는 쪽 `split_by_concepts`가 원래 하던 일이라, 우리가
개념 언저리만 잘라 보내면 그쪽이 쓸 재료가 줄어든다.

본문 조각의 단원 배정은 두 단계다.

```
① 개념 링크가 가리키는 조각 → 그 개념의 단원 (표가 갈리면 다수결, 동수면 앞 단원)
② 아무 개념도 안 가리키는 조각 → 앞 조각의 단원
```

②의 근거는 책이 순서대로라는 것뿐이다. 실측에서 배정이 거의 단조로웠고
(조각 0~5→단원0·1, 6~8→단원2, 9~11→단원3, 13~18→단원4) 빈 자리는 조각 12
하나였다. 앞뒤가 단원 3·4라 앞을 택했다 — 책은 앞 내용의 연장으로 흐른다.

조각마다 `document_id`·`filename`·`role`(skeleton\|body)을 단다. 단원 하나에
두 책의 글이 함께 오므로 화면이 출처를 구분할 수 있어야 한다.

실측 (필기 뼈대 + 실기 본문):

```
API가 보내는 것   뼈대 58,681자(조각 18/18) · 교재 76,839자(조각 21/21)   결손 0
학습 화면         목차 5 · 화면 132 · 원문 빈 화면 0
```

**재는 기준** — 교재가 100% 쓰일 필요는 없다. 뼈대(PPT)가 학습 범위고 교재는 그
흐름을 설명하는 재료다. 그래서 "교재를 몇 % 썼나"가 아니라 셋으로 나눠 본다.

| | |
| --- | --- |
| 뼈대 100% | ✅ 화면 132개 중 원문이 빈 화면 **0개** |
| 교재 가용성 100% | ✅ 조각 **21/21** · 76,839자 전부 API에 실린다 |
| 교재 활용 | 🔴 **41%** — 붙어야 할 화면 73곳 중 30곳 |

마지막 줄: 뼈대 개념 397개 중 112개에 교재 설명이 연결돼 있고, 그 개념들이 든
화면 73개 중 30개에만 교재 원문이 실린다. `grouping._source_for`가 개념명이
**제목으로** 나온 자리에서만 뽑고 화면 개념을 하나라도 못 찾으면 원문을 통째로
비우기 때문이다. 필기 개념명(`상태 패턴`)이 교재엔 영문 표(`| State |`)로 있어
안 걸린다. 우리가 고칠 자리가 아니다 — `INTEGRATION.md` §4 참고.

### 24 진단 — **시험이 아니라 설정이다**

```bash
GET   /api/courses/{id}/diagnostic          화면 ①~④ (LLM 없음, 즉시)
GET   /api/courses/{id}/diagnostic/cards    ③ 카드 4장 (LLM 1콜)
PATCH /api/courses/{id}/diagnostic          ①③ 목표·기간·형식 저장
POST  /api/courses/{id}/diagnostic/subjects ④-1 과목 단위 답 → 펼칠 과목
POST  /api/courses/{id}/diagnostic/prereqs  ④-2 펼친 과목의 항목별 답
GET   /api/courses/{id}/diagnostic/probes   ⑤ 확인 문항
POST  /api/courses/{id}/diagnostic/probes   ⑤ 채점
```

**왜 체크리스트인가** — 문항 자동 생성이 못 쓸 수준이다(실측: 책 밖 1/6 ·
책 안 1/4. 정답 번호 오류, 정답 둘, 코드 없는 코드 문제). 그래서 묻는 방식은
체크리스트이고 문항은 ⑤에서 "정말 아는지" 재는 데만 쓴다.

**⑤ 문항은 오답만 생성한다** — 실측 14/15. 차이는 하나다: LLM이 정답을 정하지
않는다. 정답은 우리가 세우고(책 밖 항목이라 원문이 없으므로 2회 생성해 유사도
0.75 이상일 때만 채택) LLM은 그걸 망가뜨리기만 한다. 만든 오답은 정답과의
유사도 0.60~0.95만 쓴다(0.98은 정답이 둘이 되고, 0.25는 아무나 골라낸다).
정답을 못 세우면 **문항을 안 낸다** — 없으면 `known`이 그대로 남을 뿐이지만,
정답이 불확실한 문항은 아는 사람을 모른다고 판정한다.

**문항 수는 고정이 아니다.** "안다"가 많을수록 몇 개 더 본다(`ceil(n/4)`, 상한 4).
점수가 아니라 자기평가가 후한지 보는 표본이라 그렇다. 틀리면 그 **과목 전체**를
`heard`로 낮춘다 — 문항 하나로 항목 하나를 판정하는 게 아니다.

**④가 두 단계인 이유** — 항목을 전부 물으면 실측 54개다. 그걸 하나씩 찍게 하면
진단이 시험이 된다. 그리고 애초에 찾으려던 건 **과목 수준의 결손**이다.

```
과목 "안다"      항목 전부 known. 안 펼친다
과목 "들어봤다"   펼친다. 항목마다 다시 묻는다
과목 "모른다"     항목 전부 unknown. 안 펼친다 (보강 단원으로 통째로 간다)
```

실측: 과목 7 → 2개만 펼침 → **7 + 23 = 30번** (전부 물으면 54번).

**과목 이름은 LLM이 합친다.** 12.5가 자료당 2회 호출의 합집합이고 코스에 자료가
여럿이라 같은 과목이 여러 이름으로 온다. 임베딩으로는 못 가른다(같음 0.806 /
다름 0.866으로 분포가 뒤집힌다 — §4). 공백 정규화로 먼저 줄이고 나머지를 LLM에
맡긴다. **판정이 아니라 병합**이라 틀려도 과목이 하나 더 남거나 덜 남을 뿐이고
항목은 하나도 안 버린다.

```
실측 (필기 + 실기)   과목 15 → 7      정리 후 이름
                    자료구조 · 객체지향 프로그래밍 · 네트워크 기초 · 운영체제 기초
                    데이터베이스 기초 · 정보 보안 기초 · 컴퓨터 기초
```

⚠️ **③ 성향에 학습 효과 근거는 없다.** 러닝 스타일 맞춤(meshing hypothesis)은
반증됐다(Pashler 2008). 이건 성취가 아니라 **이탈**을 막는 장치다 — 읽기 싫은
형식이면 안 읽는다. 화면 문구도 "당신에게 맞는 학습법"이 아니라 **"어떤 설명이
읽기 편한가"**여야 한다. 자기평가 진술문("나는 비유를 좋아한다")을 안 쓰는 이유는
실측 4/6이기도 하고, 무엇보다 사람들이 자기 스타일을 잘 모르기 때문이다 —
실물 넷을 보여주고 고르게 한다.

**② 분야 확인이 12.5의 유일한 검증 창구다.** 분야 판정은 자동으로 검증할 방법이
없다(§5). 여기서 사용자가 아니라고 하면 직접 입력받는다.

## 5. 알려진 한계

- **목차 품질** — 얇은 자료는 조각 예산을 줄여 목차 재료를 확보하지만
  (network 4조각 → 15조각), 43슬라이드에 단원 3개는 성길 수 있다.
  슬라이드 제목이 조각 heading으로 남아 있어 2단 목차로 확장할 재료는 된다.
- **density 문턱 800자/페이지** — 표본 3권 기준이다. 뼈대 최댓값 321과 본문
  최솟값 1,266 사이가 넓어 위치를 더 재봐야 한다.
- **끊긴 고리는 결손 판정에 못 쓴다 (16번 폐기)** — pilgi의 55개를 전부 봤더니
  `행동 패턴`(11회)·`릴레이션`(5)·`데이터베이스`(3)·`변수`·`제어문`처럼 **그 책이
  가르치는 내용**이 대부분이었다. 목차에 "3. 데이터베이스 구축"이 있는데
  `데이터베이스`가 끊긴 고리로 잡히는 식이다. 개념↔조각 연결이 누락돼 끊긴 것처럼
  보였을 뿐이고, `insertion-sort` 같은 영문 슬러그가 한글 개념과 중복으로 섞여
  있기도 하다. 그리고 근본적으로 **책이 언급조차 안 한 선수는 원문에서 나올 수가
  없다.** 그래서 방향을 뒤집어 12.5단계(위→아래 분야 판정)로 대체했다.
  `GET /courses/{id}/gaps`는 참고용으로 남겨 뒀다.
- **분야 판정은 재현되지 않는다** — 같은 자료를 두 번 물으면 개수부터 다르다
  (pilgi 6개 vs 2개). 교집합으로 거르려 했으나 과목 이름은 임베딩으로 못
  가른다는 게 실측으로 확인됐다 — `AWS 기본 개념`↔`AWS 기본 서비스`(같음, 0.806)
  와 `네트워크 보안 기초`↔`네트워크 기초`(다름, 0.866)가 겹친다. 그래서 2회
  **합집합**을 취하고 거르는 일은 뒤의 기각 검사에 맡긴다. 놓치면 복구가 안 되고
  (교집합으로 돌렸을 때 network의 `Linux 기초`가 사라졌다) 헛것은 뒤에서 걸린다.
- **회색지대 LLM 판정이 흔들린다** — 16'에서 `라우팅 원리`가 실행마다 통과와
  기각을 오갔다. 그래서 LLM이 항목을 **지우지 못하게** 했다(gray로만 표시).
  최종 확인은 24번 사용자 확인 화면이 한다.
- **연결이 27%에 그친다** — pilgi 452개 중 120개. 필기와 실기는 범위가 달라서
  정상이지만, 뼈대에만 있고 본문에 없는 개념은 26번 조달 대상이다.
- **`ai_prereq`는 딱지일 뿐** — 책 밖 개념이라는 표시지 실제로 외부에서
  가져온 내용이 아니다. `origin: preload`는 26번이 생겨야 채워진다.
- **users 테이블이 없다** — `course.user_id`와 `user_documents.user_id`에 FK를
  못 걸고 있고, 코스 생성 시 클라이언트가 `user_id`를 직접 준다.
- 🔴 **교재 설명이 붙어야 할 화면의 41%에만 붙는다** — 연결된 개념 112개가 든
  화면 73개 중 30개. 개념명이 제목으로 나온 자리에서만 뽑고, 화면 개념을 하나라도
  못 찾으면 원문을 비우는 규칙 때문이다(`grouping._source_for`).
  **학습 담당이 정할 일이다.** 한때 우리 쪽에서 개념명 언저리를 창으로 잘라 억지로
  붙였으나 걷어냈다 — 화면을 만드는 건 우리 층이 아니고, 자르면 그쪽이 쓸 재료가 준다.
- **교재는 100%가 목표가 아니다** — 뼈대(PPT)가 학습 범위고 교재는 그 흐름을
  설명하는 재료다. 그래서 "교재를 몇 % 썼나"로 재면 안 된다. 실측에서 교재를
  **혼자** 올리면 원문 활용이 148%(문단이 여러 화면에 겹침)인데, 같은 책이 코스의
  본문 역할이면 낮게 나온다 — 자르는 이름이 뼈대 개념명이라 그렇고, 정상이다.
  한때 교재 개념을 단원에 함께 실어 회수율을 올리려 했으나 접었다 — 화면이 132→320개로
  늘고 **교재가 별도 커리큘럼이 된다.** 그러면 PPT가 정한 흐름이 깨진다.
- **`source_topic_id`가 NULL인 코스 단원은 개념이 없다** — 보강 단원
  (`origin=inserted`)이 그 자리다. 예전에는 사전을 그냥 조회해 **목차 배정에
  실패한 고아 개념**이 딸려 왔다(실측: AWS 코스 단원 셋에 같은 고아 11개가 세 번
  반복). 지금은 빈 단원으로 둔다 — 내용은 26번이 채운다.
- **개발 DB에 08-05에 만든 코스 둘이 `source_topic_id` 없이 남아 있다**
  (`네트워크 수업`, `[꿈꾸는라이언]…`). 지금 `copy_topics`는 항상 채우므로 코드
  문제가 아니라 낡은 데이터다. 열면 화면 0개로 보인다 — 지우고 다시 만들면 된다.
