# MetaLearn — 문제 생성 품질 튜닝 기록

> 스모크 실측(16회차까지)으로 문항 품질을 끌어올린 **시간순 실험 기록**.
> 설계 자체는 [QUIZ.md](QUIZ.md), 입력 계약은 [QUIZ_INPUT.md](QUIZ_INPUT.md),
> 세션별 일지는 [WORKLOG.md](WORKLOG.md) 참고.

## 지금 유효한 결론 (여기만 읽어도 됨)

시간순 기록이라 앞 섹션일수록 낡았다. §1~6은 초기 프롬프트 튜닝의 역사,
**현재 구조의 근거는 §8(검증기 캡슐화)·§10(배심원단)·§12(pro3 전환)**이다.

- **모델은 solar-pro3 단독** (08-07 확정, pro2 미사용). 전환 과정·실측은 §12.
  1~12회차 수치는 전부 pro2 기준이라 pro3와 직접 비교하면 안 된다.
- **현재 검증 구조**: sN 스크럽 → 기계 검사 → 심판 Solar+EXAONE → 풀이 왕복
  Solar+EXAONE → 불합격 수정 1회 → 재검. 어느 한쪽이 잡으면 탈락,
  EXAONE 판독 불가는 기권 (§10.3). 모든 Solar 콜은 json_object 래퍼 계약 (§12.2)
- **핵심 교훈 두 개**: LLM을 설득하는 것보다 코드로 막는 게 확실하다(§5-②) ·
  심판의 설명보다 풀이자의 실험이 잘 잡는다(§8)
- **최신 실측** (19회차, §12.5): **저장 21/폐기 21 — pro2 기준(11) 초과.**
  pro3 네이티브 재구성 3종(cloze 코드 조립·풀이 관용·few-shot 프롬프트)의 결과.
  cloze는 LLM이 아니라 코드가 조립한다 (`build_cloze_segments`)
- **남은 관찰**: 회차 간 분산 큼(대표본 재확인 권장) · cloze 수율 낮음 ·
  서빙 층화 샘플링 (count가 작을수록 유형 쏠림 — WORKLOG 남은 개선) — §12.6
- **운영 주의**: `.env`는 UTF-8 필수(§0) · EXAONE은 dedicated 엔드포인트 필수(§10.2) ·
  품질 지표는 폐기율이 아니라 "저장분 중 실사용 가능 비율"(§7)

## 0. 먼저 알아야 할 것 — `.env` 인코딩

`backend/.env`가 **UTF-16 LE**로 저장돼 있어 `python-dotenv`가 UTF-8로 읽다
`UnicodeDecodeError`로 죽었다. `UPSTAGE_API_KEY`는 들어 있었지만 스모크 테스트가
시작조차 못 하는 상태였다. UTF-8(BOM 없음)로 변환해 해결했고 원본은
`backend/.env.utf16.bak`에 백업(`.gitignore`의 `.env.*`로 무시됨).

> PowerShell에서 `... > .env` 리다이렉트로 만들면 UTF-16으로 저장돼 재발한다.
> `Out-File -Encoding utf8` 또는 에디터에서 UTF-8 지정할 것.

## 3. `prompts.py`에서 고친 것 (이번 커밋 범위)

생성 규칙 4 → 12개, 심판 체크 3 → 11개로 확장. **실행으로 효과가 확인된 것:**

- ✅ 발문 시험 문체 · mcq 선지 정확히 4개 → 3회차 이후 100% 준수
- ✅ 단답 정답을 용어(25자 이내)로, `"정의를 쓰시오"`가 아닌 **설명 → 용어** 방향
- ✅ 특수문자·수식 정답은 `aliases`에 키보드 입력 가능한 표기 병기
  → LOC 수식 문항이 폐기 → 저장으로 전환
- ✅ 빈칸 개수 제한(1~2개) + 순서 무관 나열 금지
- ✅ 발문·해설에 내부 문장 번호(`s38`) 노출 금지 (3회차에서 새로 생긴 회귀를 4회차에 차단)

**프롬프트로 못 고친 것** — 6회차에 남은 결함 4건은 **전부 cloze**다:

- 답이 지문에 그대로 노출: `"개발 단계별 인월 수는 … 생명 주기 각 단계별로 [인월 수]를 산정한다"`
- 사실 오류: LOC 공식에서 `/6`이 빠짐 (원문은 `(a+4c+b)/6`)
- `aliases`에 넣은 단어가 지문 text에 이미 보임 (`Sprint` / `또는 Iteration`)

> 규칙을 하나 추가할 때마다 다른 곳에서 새 결함이 나오는 두더지잡기 상태라 여기서 멈췄다.
> **다음 개선은 프롬프트가 아니라 §5의 코드 쪽에서 해야 한다.**

## 5. 남은 작업 (우선순위 순)

이번 커밋은 `prompts.py`만 건드렸다. 아래는 **손대지 않았다.**

### ① `classify_form` 오분류 — 효과 가장 큼

`planning.py:27`의 `re.search(r"단계|순서(?:로|대로)", text)`가 이름에 "단계"만 들어가도
`sequence`로 판정한다. 픽스처 기준 **개념 6개 중 4개가 오분류**:

```
sequence     ['cloze']  소프트웨어 생명 주기
sequence     ['cloze']  애자일 모형
sequence     ['cloze']  LOC 기법
sequence     ['cloze']  개발 단계별 인월 수      ← "단계" 때문
definition   ['shortAnswer']  프로젝트 비용 산정 기법
enumeration  ['mcq']  익스트림 프로그래밍
```

`FORM_TYPE_CANDIDATES`에서 `sequence → ["cloze"]` 단일 매핑이라(`schemas.py:18`)
cloze가 강제된다. 설정값(`type_ratio` = mcq 0.4 / cloze 0.25)과 정반대이고,
**불량 문항은 거의 전부 이 cloze들이다.** cloze는 순서·완전일치 채점이라 가장 취약한
유형인데 가장 많이 생성되고 있다.

→ 단순 키워드 매칭 대신 실제 절차 나열(`→`/`▶` 2회 이상 등)만 `sequence`로 볼 것.

### ② 기계 검사 강화 — 프롬프트보다 결정적

`generation.py:76`의 `mechanical_check`에 추가할 것. LLM을 설득하는 것보다 코드로
막는 쪽이 확실하다:

- 빈칸 `answer`(또는 `aliases`)가 같은 문항의 `text` 세그먼트에 노출되면 폐기
- mcq `len(options) != 4` 폐기 (현재 `>= 2`만 검사)
- `aliases`가 `answer`와 동일하면 정리 (6회차에서 중복 발생)

### ③ 생성 실패 로깅

§4 참고. 파싱 실패 시 `logger.warning` + 조각 단위 재시도 또는 리포트에 명시.

## 5.5 후속 처리 완료 (08-05, 웹 세션)

§5의 ①②③ 모두 코드로 반영했다:

- **① classify_form**: "단계|순서" 키워드 매칭 제거 → 근거 원문에 화살표류(→▶) 구분자
  2회 이상일 때만 `sequence`. 추가로 `sequence → ["cloze","mcq"]`로 후보를 넓혀 cloze
  강제를 해소. 픽스처 기준 오분류 4건 전부 해소, cloze 비중 6/6 → 1/6.
- **② mechanical_check**: mcq 선지 정확히 4개 강제(≠4 폐기), cloze 정답/별칭이 지문
  text에 노출되면 폐기, answer와 동일한 alias 자동 정리.
- **③ 생성 실패**: 응답 파싱 실패 시 `logger.warning` + 조각 단위 1회 재시도, 그래도
  비면 리포트(`discarded`)에 "생성 응답 파싱 실패"로 명시 — 조용한 실패 제거.

회귀 테스트로 고정: `test_classify_form_does_not_overfire_sequence`,
`test_mechanical_check_rejects_cloze_answer_leaked_in_text`,
`test_generation_parse_failure_retries_then_reports` 외 (총 42개 통과).

→ 확인 결과는 §7 참고 — 실제로 올랐다.

## 7. 대표본 검증 — §5.5 반영 후 (08-05, 7회차)

`--chunks 3 --budget 20`으로 실행. **저장 27 / 폐기 5** (폐기율 16%).

| 지표 | 6회차 (수정 전) | 7회차 (수정 후) |
| --- | --- | --- |
| 실사용 가능 | 2/6 (33%) | **15/27 (56%)** |
| 구조적 결함 (채점 불가·정답 유일성 붕괴) | 4건 | **0건** |
| 유형 분포 | cloze 6/6 강제 | mcq 11 / 단답 8 / cloze 5 / 참거짓 3 — 설정값 수렴 |

§5.5의 효과 확인:

- ①: 유형 배분이 `type_ratio`(mcq 0.4 / cloze 0.25)에 수렴, 채점 불가 문항 소멸
- ②: 새 기계 검사가 실전 작동 — "cloze 정답 'Partial Functional Dependency'이 지문에 노출됨" 폐기
- ③: 조용한 실패 없음. 심판 폐기 사유도 정확해짐 ("완전일치 채점 기준 위반", "정답 유일성 미확보")

### 남은 결함 12건 중 10건 = 문장 번호 유출 (한 조각 전멸 패턴)

목차 1(조각 2)의 저장 문항 10개 **전원**의 해설에 내부 문장 번호가 노출됐다
(`"s27에 따라 트랜잭션은…"`). 조각 1의 17문항은 전부 깨끗함 — **생성 콜 1회가
규칙 8을 통째로 무시**했고 심판(Q9)도 전부 놓쳤다. 프롬프트로 막을 수 없는 LLM 편차.

→ `mechanical_check`에 유출 검사 추가로 대응 (이 커밋). 주의: `\bs\d+\b`는 한글이
유니코드 단어문자라 `"s27에"`를 못 잡는다 — 룩비하인드 `(?<![0-9A-Za-z])s\d+` 사용,
대문자(AWS S3 등 정상 용어)는 제외. 이 검사 적용 시 7회차 기준 실사용 비율 56% → **~89%**.

나머지 2건 (미해결, 빈도 낮음):

- COCOMO cloze가 원문 조각(`"① COCOMO … : 보헴 제안 / [빈칸] →"`)을 그대로 지문으로 사용 — 비문
- CPM 단답의 evidence 문장이 PERT 행을 가리킴 — 근거 표시가 엉뚱한 내용 (개념-문장 매칭 한계)

## 8. 검증기 캡슐화 + 연구 기법 3종 도입 (08-05, 웹 세션)

에듀테크·연구 사례 조사(NotebookLM 근거 인용, overgenerate-and-rank arXiv:2405.05144,
critique-revise 다중 에이전트, answerability round-trip) 후 반영:

**캡슐화** — 검증 전체를 `app/core/quality/`로 이동. 입력 계약은 "문항 + 근거 텍스트 +
LLM"뿐이라 **학습 페이지(JIT·진단·형성평가) 문항도 같은 `validate_items()`를 호출**하면
된다. quiz 쪽은 문장 번호↔근거 텍스트 변환 어댑터(`features/quiz/generation.py`)만 유지.
기존 `features/quiz/grading.py`·`serving.py`는 core 재노출 셔틀로 축소 (하위 호환).

**새 단계 3개** (기존 기계검사·심판 위에):

1. **풀이 왕복 검증** — 정답 가린 문항을 풀이자 LLM이 근거만 보고 풀고, 채점기
   (`core/quality/grading.py` — 서빙과 동일 규칙)로 판정. mcq는 "정답으로 보이는
   번호 전부"를 답하게 해 복수 정답을 실험으로 잡는다. 심판이 놓치던 유일성 붕괴
   (§1의 6회차 패턴)의 직접 대응.
2. **불합격 수정 1회** — 폐기 대신 사유 첨부 재작성 → 전체 배터리 재검사.
   폐기율로 인한 커버리지 구멍(문항 0개 개념) 완화.
3. **오답 선지 과생성+선별** — 생성 프롬프트가 `distractorPool`(후보 {text,why})을
   추가로 받고, 코드가 중복·정답동치 제거 + 길이 동질성으로 3개 선별 + 결정적 셔플.

콜 수 영향: 조각당 +1(풀이자 묶음) + 불합격 있을 때 +1~2(수정+재검사). 전체 ~40% 증가.

### 10.2 EXAONE(friendli) 인프라 이슈 3종 — 전부 해결

   `EXAONE_MODEL=<Endpoint ID>` 설정으로 제한·토큰 캡 둘 다 소멸.

3. **심판 형식 붕괴**: reason 필드에 장문 검토를 쓰다 JSON이 깨짐, index 누락,

### 10.3 왜 단독 교체가 아니라 배심원단인가

  - 심판·풀이 각각 Solar(1차) + EXAONE(2차) — **어느 한쪽이 잡으면 탈락**
  - **2차의 판독 불가 응답은 기권** (1차 판정 유지) — 형식 난조가 학살로 안 이어짐

  - 수정은 생성 모델(Solar), 재검은 같은 배심원단

진단(§12.5)이 더 근본적이어서 **pro3 네이티브 재구성**으로 방향 전환.

### 12.5 pro3 네이티브 재구성 — 수율 회복 (08-07, 18·19회차)

"파이프라인이 pro2 실패 이력에 맞춰 튜닝된 것 아닌가"라는 가설(사용자)에 따라
pro2 흔적 세 곳을 재설계:

1. **cloze를 코드가 만든다** (`generation.py::build_cloze_segments`) — LLM은
   `{"sentence":"sN","answer":용어}`로 "어느 문장의 어떤 용어"만 고르고, 지문
   자르기·빈칸 뚫기·정답 제거는 코드가 결정적으로 수행. 정답이 문장에 0회/2회면
   폐기(위치 모호). pro3 cloze 불량 전 계열(원문 통째+빈칸 덧붙임·정답 노출·기호
   빈칸)이 생성 단계에서 소멸. **cloze는 수정 루프에서도 제외** — LLM 재작성이
   segments를 다시 만들면 노출을 재생산한다(18회차 실측 3건).
2. **풀이 대조 관용** (`checks.py::check_solution`) — 왕복 검증의 목적은 "풀 수
   있는 문항인가"지 표기 시험이 아니다. '용어 (병기)' 괄호 제거, '용어+접미
   수식'(startswith, 군더더기 ≤15자), mcq "2번" 표기, cloze 문자열 답변을 내용
   기준으로 재채점.
3. **생성 프롬프트 백지 재작성** — pro2 실패 이력의 금지 나열 12개 → 핵심 계약
   7개 + **모범 출력 few-shot 예시**(형식만, 내용 복사 금지 명시). 기계 검사가
   잡는 항목은 프롬프트에서 뺐다.

효과 분리 실측: ①② → 저장 2→8 (18회차), ③ → 8→**21** (19회차). ③(few-shot)의
기여가 가장 컸다 — 추론형 모델은 금지 나열보다 모범 예시에 반응한다는 가설 부합.

19회차 저장 21건 스팟 체크: 발문·문체 정상, mcq 9/단답 7/OX 4/cloze 1.
폐기 21건도 대부분 정당(같은 개념 중복 출제 검출·정답 유일성·근거 불일치).

### 12.6 남은 관찰 사항

- pro3 풀이자가 배치 JSON을 간헐적으로 깨뜨림 (19회차: `["로킹 단위"}` 괄호 불일치)
  — 잘린 배열 구제가 일부 살리고, 나머지는 재검에서 회복되거나 폐기. 빈도 낮음.
- cloze 수율이 낮음 (조립 조건이 엄격) — 유형 배분상 문제없으나, 늘리려면
  "정답이 문장에 2번"일 때 첫 등장만 비우는 완화를 검토할 수 있다.
- 회차 간 분산: 재구성 후 3회 반복(19·20·21회차) 저장 21/14/18 — **최저치(14)도
  pro2 기준(11)을 넘음.** 결론 안정.
- **산식 결과 빈칸 차단** (08-08, 실기 노트 실측): "64 − 2 = [빈칸]"처럼 빈칸이
  계산 결과 자리면 지문이 답을 산수로 노출한다 — 풀이자 LLM도 계산해 맞히므로
  왕복 검증이 못 잡는 맹점. 기계 검사에 "빈칸 직전이 =/≒/≈면 폐기" 추가.
  같은 문항에서 위첨자 손실(2⁶→"26")도 관찰 — 이건 파싱(OCR) 층 이슈로
  파싱 파트 공유 필요 (검증은 원문 충실성만 보므로 원문이 깨지면 못 잡음).
