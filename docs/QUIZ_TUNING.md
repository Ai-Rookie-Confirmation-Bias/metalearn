## 0. 먼저 알아야 할 것 — `.env` 인코딩

`backend/.env`가 **UTF-16 LE**로 저장돼 있어 `python-dotenv`가 UTF-8로 읽다
`UnicodeDecodeError`로 죽었다. `UPSTAGE_API_KEY`는 들어 있었지만 스모크 테스트가
시작조차 못 하는 상태였다. UTF-8(BOM 없음)로 변환해 해결했고 원본은
`backend/.env.utf16.bak`에 백업(`.gitignore`의 `.env.*`로 무시됨).

> PowerShell에서 `... > .env` 리다이렉트로 만들면 UTF-16으로 저장돼 재발한다.
> `Out-File -Encoding utf8` 또는 에디터에서 UTF-8 지정할 것.

## 3. `prompts.py`에서 고친 것 (이번 커밋 범위)

생성 규칙 4 → 12개, 심판 체크 3 → 11개로 확장. **실행으로 효과가 확인된 것:**

- ✅ 발문 시험 문체 · mcq 선지 정확히 4개 → 3회차 이후 100% 준수
- ✅ 단답 정답을 용어(25자 이내)로, `"정의를 쓰시오"`가 아닌 **설명 → 용어** 방향
- ✅ 특수문자·수식 정답은 `aliases`에 키보드 입력 가능한 표기 병기
  → LOC 수식 문항이 폐기 → 저장으로 전환
- ✅ 빈칸 개수 제한(1~2개) + 순서 무관 나열 금지
- ✅ 발문·해설에 내부 문장 번호(`s38`) 노출 금지 (3회차에서 새로 생긴 회귀를 4회차에 차단)

**프롬프트로 못 고친 것** — 6회차에 남은 결함 4건은 **전부 cloze**다:

- 답이 지문에 그대로 노출: `"개발 단계별 인월 수는 … 생명 주기 각 단계별로 [인월 수]를 산정한다"`
- 사실 오류: LOC 공식에서 `/6`이 빠짐 (원문은 `(a+4c+b)/6`)
- `aliases`에 넣은 단어가 지문 text에 이미 보임 (`Sprint` / `또는 Iteration`)

> 규칙을 하나 추가할 때마다 다른 곳에서 새 결함이 나오는 두더지잡기 상태라 여기서 멈췄다.
> **다음 개선은 프롬프트가 아니라 §5의 코드 쪽에서 해야 한다.**

## 5. 남은 작업 (우선순위 순)

이번 커밋은 `prompts.py`만 건드렸다. 아래는 **손대지 않았다.**

### ① `classify_form` 오분류 — 효과 가장 큼

`planning.py:27`의 `re.search(r"단계|순서(?:로|대로)", text)`가 이름에 "단계"만 들어가도
`sequence`로 판정한다. 픽스처 기준 **개념 6개 중 4개가 오분류**:

```
sequence     ['cloze']  소프트웨어 생명 주기
sequence     ['cloze']  애자일 모형
sequence     ['cloze']  LOC 기법
sequence     ['cloze']  개발 단계별 인월 수      ← "단계" 때문
definition   ['shortAnswer']  프로젝트 비용 산정 기법
enumeration  ['mcq']  익스트림 프로그래밍
```

`FORM_TYPE_CANDIDATES`에서 `sequence → ["cloze"]` 단일 매핑이라(`schemas.py:18`)
cloze가 강제된다. 설정값(`type_ratio` = mcq 0.4 / cloze 0.25)과 정반대이고,
**불량 문항은 거의 전부 이 cloze들이다.** cloze는 순서·완전일치 채점이라 가장 취약한
유형인데 가장 많이 생성되고 있다.

→ 단순 키워드 매칭 대신 실제 절차 나열(`→`/`▶` 2회 이상 등)만 `sequence`로 볼 것.

### ② 기계 검사 강화 — 프롬프트보다 결정적

`generation.py:76`의 `mechanical_check`에 추가할 것. LLM을 설득하는 것보다 코드로
막는 쪽이 확실하다:

- 빈칸 `answer`(또는 `aliases`)가 같은 문항의 `text` 세그먼트에 노출되면 폐기
- mcq `len(options) != 4` 폐기 (현재 `>= 2`만 검사)
- `aliases`가 `answer`와 동일하면 정리 (6회차에서 중복 발생)

### ③ 생성 실패 로깅

§4 참고. 파싱 실패 시 `logger.warning` + 조각 단위 재시도 또는 리포트에 명시.

## 5.5 후속 처리 완료 (08-05, 웹 세션)

§5의 ①②③ 모두 코드로 반영했다:

- **① classify_form**: "단계|순서" 키워드 매칭 제거 → 근거 원문에 화살표류(→▶) 구분자
  2회 이상일 때만 `sequence`. 추가로 `sequence → ["cloze","mcq"]`로 후보를 넓혀 cloze
  강제를 해소. 픽스처 기준 오분류 4건 전부 해소, cloze 비중 6/6 → 1/6.
- **② mechanical_check**: mcq 선지 정확히 4개 강제(≠4 폐기), cloze 정답/별칭이 지문
  text에 노출되면 폐기, answer와 동일한 alias 자동 정리.
- **③ 생성 실패**: 응답 파싱 실패 시 `logger.warning` + 조각 단위 1회 재시도, 그래도
  비면 리포트(`discarded`)에 "생성 응답 파싱 실패"로 명시 — 조용한 실패 제거.

회귀 테스트로 고정: `test_classify_form_does_not_overfire_sequence`,
`test_mechanical_check_rejects_cloze_answer_leaked_in_text`,
`test_generation_parse_failure_retries_then_reports` 외 (총 42개 통과).

→ 확인 결과는 §7 참고 — 실제로 올랐다.

### 남은 결함 12건 중 10건 = 문장 번호 유출 (한 조각 전멸 패턴)

목차 1(조각 2)의 저장 문항 10개 **전원**의 해설에 내부 문장 번호가 노출됐다
(`"s27에 따라 트랜잭션은…"`). 조각 1의 17문항은 전부 깨끗함 — **생성 콜 1회가
규칙 8을 통째로 무시**했고 심판(Q9)도 전부 놓쳤다. 프롬프트로 막을 수 없는 LLM 편차.

→ `mechanical_check`에 유출 검사 추가로 대응 (이 커밋). 주의: `\bs\d+\b`는 한글이

## 8. 검증기 캡슐화 + 연구 기법 3종 도입 (08-05, 웹 세션)

에듀테크·연구 사례 조사(NotebookLM 근거 인용, overgenerate-and-rank arXiv:2405.05144,
critique-revise 다중 에이전트, answerability round-trip) 후 반영:

**캡슐화** — 검증 전체를 `app/core/quality/`로 이동. 입력 계약은 "문항 + 근거 텍스트 +
LLM"뿐이라 **학습 페이지(JIT·진단·형성평가) 문항도 같은 `validate_items()`를 호출**하면
된다. quiz 쪽은 문장 번호↔근거 텍스트 변환 어댑터(`features/quiz/generation.py`)만 유지.
기존 `features/quiz/grading.py`·`serving.py`는 core 재노출 셔틀로 축소 (하위 호환).

**새 단계 3개** (기존 기계검사·심판 위에):

1. **풀이 왕복 검증** — 정답 가린 문항을 풀이자 LLM이 근거만 보고 풀고, 채점기
   (`core/quality/grading.py` — 서빙과 동일 규칙)로 판정. mcq는 "정답으로 보이는
   번호 전부"를 답하게 해 복수 정답을 실험으로 잡는다. 심판이 놓치던 유일성 붕괴
   (§1의 6회차 패턴)의 직접 대응.
2. **불합격 수정 1회** — 폐기 대신 사유 첨부 재작성 → 전체 배터리 재검사.
   폐기율로 인한 커버리지 구멍(문항 0개 개념) 완화.
3. **오답 선지 과생성+선별** — 생성 프롬프트가 `distractorPool`(후보 {text,why})을
   추가로 받고, 코드가 중복·정답동치 제거 + 길이 동질성으로 3개 선별 + 결정적 셔플.

콜 수 영향: 조각당 +1(풀이자 묶음) + 불합격 있을 때 +1~2(수정+재검사). 전체 ~40% 증가.
테스트 55개 통과.

## 9. 8회차 — 새 검증 배터리 실측 (08-05, `--chunks 3 --budget 20`)

**저장 27 / 폐기 14 · 실사용 가능 ~20/27 (74%)** — 7회차 56%에서 상승, 기대(~89%) 미달.

새 장치가 실전에서 일한 증거:

- `[solve]` 풀이 왕복이 **복수 정답을 실험으로 검출** (FP mcq: 풀이자 [1,2] 판단),
  발문 모호(LOC→'PUTNAM 기법'), accepted 표기 불일치(MAC) 검출 — 심판이 놓치던 것들
- 수정 루프: sN 유출 문항 다수를 수정 시도, 회생 실패만 최종 폐기.
  **저장분 중 sN 노출 0건** (7회차는 10건)
- 폐기 사유가 단계 태그(`[mechanical]`/`[judge]`/`[solve]`)로 정확해짐

### 남은 결함 7건 = 기존 미해결 2패턴 (§7 끝부분)이 이제 주범

1. **근거 오매칭 4건** — 문항은 멀쩡한데 📎 근거가 엉뚱 (CPM→PERT 행 재현,
   독립성→뷰 설명, 애자일→개발모형 표, 순수 관계 연산자→헤더 한 줄).
   심판·풀이자 모두 "주어진 근거" 기준으로 판정하므로 **근거 자체의 오류는 검증
   배터리가 구조적으로 못 잡는다** → 선별(selection) 단계에서 고쳐야 함.
2. **cloze 구절 통째 빈칸 3건** — "계획 수립 → 위험 분석 → 개발 및 검증 → 고객 평가"
   전체가 빈칸. 사람은 완전일치로 못 맞히는데 **풀이자 LLM은 근거 원문을 보고
   복사할 수 있어 solve를 통과** — 풀이 왕복의 맹점. 기계 검사로 막아야 함.
